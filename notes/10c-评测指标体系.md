## Step 1: 基础指标——Precision、Recall、F1

这三个是所有评测指标的地基。后面的 BLEU、ROUGE、pass@k 本质上都是在不同粒度上复用 precision/recall 的思想。

在 LLM 评测中最常见的用法是 **token 级 F1**（SQuAD 等抽取式 QA 的标准指标）：把 gold answer 和 model answer 各拆成 token 集合，看共享了多少。

```
Gold answer:  "北京是中国的首都"    → tokens: {北京, 是, 中国, 的, 首都}  共 5 个
Model answer: "中国首都是北京"      → tokens: {中国, 首都, 是, 北京}      共 4 个

共同 tokens: {北京, 是, 中国, 首都} = 4 个
```

$$\text{Precision} = \frac{\text{共同 tokens}}{\text{模型输出的 tokens}} = \frac{4}{4} = 1.0$$

"模型输出的 4 个 token 全在 gold 里"——模型没有瞎说（没有误报）。

$$\text{Recall} = \frac{\text{共同 tokens}}{\text{Gold 的 tokens}} = \frac{4}{5} = 0.8$$

"gold 的 5 个 token 里模型覆盖了 4 个，漏了'的'"——模型漏掉了一些信息。

$$F_1 = \frac{2 \times P \times R}{P + R} = \frac{2 \times 1.0 \times 0.8}{1.0 + 0.8} = \frac{1.6}{1.8} = 0.89$$

F1 是 Precision 和 Recall 的**调和平均**。为什么不用普通的算术平均 $(P + R) / 2 = 0.9$？因为调和平均**对低值更敏感**——如果 P 和 R 有一个很差，F1 会被拉得很低，不会被另一个高值"掩盖"：

```
P = 1.0, R = 0.2:
  算术平均 = (1.0 + 0.2) / 2 = 0.6   ← 看起来还行？
  F1      = 2*1.0*0.2 / 1.2  = 0.33  ← 真实反映了"你漏了太多"
```

这保证了 **F1 高时两个指标都不差**。

## Step 2: 文本生成质量指标——BLEU 和 ROUGE

BLEU 和 ROUGE 是 LLM 之前 NLP 时代最重要的生成评测指标。现在用得少了（LLM 生成太灵活，表面文字匹配意义不大），但面试还会问。

**一句话区分**：

```
BLEU  → Precision → "我生成的东西，有多少在参考答案里" → 翻译（别瞎翻）
ROUGE → Recall    → "参考答案里的东西，我覆盖了多少" → 摘要（别漏信息）
```

一个例子走完两个：

```
参考: "猫 坐 在 垫子 上"    （5个词）
生成: "猫 在 垫子"          （3个词）

BLEU  看 Precision: 生成了3个词，3个都在参考里 → 3/3 = 1.0（没瞎说）
ROUGE 看 Recall:    参考有5个词，你只覆盖了3个 → 3/5 = 0.6（漏了东西）
```

### 2.1 BLEU（Bilingual Evaluation Understudy）细节

**BLEU 和裸 Precision 的区别**：BLEU 本质就是 Precision，但多了两样东西：

1. **多粒度**：同时看 1/2/3/4-gram 的 precision，取几何平均（所以叫 BLEU-4）。只要有一个级别 = 0，整个 BLEU = 0，非常严格
2. **Brevity Penalty（BP）**：生成比参考短就罚分，防止只输出几个高置信词来刷 precision

$$\text{BLEU} = \underbrace{\text{BP}}_{\text{长度惩罚}} \cdot \exp\left(\sum_{n=1}^{N} \frac{1}{N} \log p_n\right)$$

- $p_n$ = n-gram precision（生成的 n-gram 中有多少出现在参考里）
- $N$ = 通常取 4（所以叫 BLEU-4），$1/N$ 是均匀权重
- $\exp(\frac{1}{N}\sum \log p_n)$ = 各级 precision 的**几何平均**（任何一个 $p_n = 0$ 则整体 = 0）
- $\text{BP} = \begin{cases} 1 & c > r \\ e^{1 - r/c} & c \leq r \end{cases}$，$c$ = 生成长度，$r$ = 参考长度，生成太短就罚分

> **BLEU/ROUGE 在 LLM 时代的残余用途**：虽然不再适合评测 LLM 生成质量，但 n-gram 重叠的思想仍然用于**预训练语料筛选**：(1) **去重**——用 n-gram 重叠率（MinHash + n-gram）找出高度重复的文本；(2) **去污染（decontamination）**——剔除和 benchmark 测试集过于相似的训练样本，防止评测分数虚高（GPT-4、Llama 技术报告都提到了这一步）。

### 2.2 ROUGE-L——最常用的 ROUGE 变体

ROUGE 有 ROUGE-1/2/L 几种变体，最常用的是 **ROUGE-L**，用**最长公共子序列（LCS）** 来衡量。

LCS 的意思：两个句子里都出现、且保持先后顺序的最长 token 序列（不需要连续）。

```
参考: "猫 坐 在 垫子 上"    （5个词）
生成: "猫 在 垫子 旁"       （4个词）

LCS = "猫 在 垫子" = 3 个词
（"猫"在"在"前面，"在"在"垫子"前面——两边都满足这个顺序）
```

**为什么 ROUGE "是 Recall 导向"但还要报 Precision 和 F1？**

ROUGE 的名字里 R = Recall-Oriented，意思是它的**设计初衷**是衡量召回率（摘要有没有漏掉重要信息）。但只看 Recall 有漏洞——模型把参考答案原封不动抄一遍再加一堆废话，Recall = 1.0 但质量很差。所以实际使用时 ROUGE 也算 Precision，最终报 **F1**（P 和 R 的调和平均）。

**ROUGE-L 的公式**（设 LCS 长度为 $l$，参考长度为 $m$，生成长度为 $n$）：

$$R_{\text{lcs}} = \frac{l}{m}, \quad P_{\text{lcs}} = \frac{l}{n}, \quad F_{\text{lcs}} = \frac{2 \cdot R_{\text{lcs}} \cdot P_{\text{lcs}}}{R_{\text{lcs}} + P_{\text{lcs}}}$$

**所以 ROUGE-L 到底是什么？** 答案是 **F1**。名字叫 Recall-Oriented 是因为出发点看 Recall，但最终报的分数是 F1。

代入上面的例子：

```
LCS = 3, 参考长度 m = 5, 生成长度 n = 4

R = 3/5 = 0.60  ← 参考里的内容覆盖了多少（Recall，设计初衷）
P = 3/4 = 0.75  ← 生成的内容有多少是有用的（Precision，防止灌水）
F1 = 2 * 0.60 * 0.75 / (0.60 + 0.75) = 0.67  ← 实际报这个
```

### 2.3 BERTScore——用语义替代表面匹配

BLEU 和 ROUGE 的根本问题是只看文字表面——"我喜欢猫"和"我爱猫"意思一样但得分很低。

BERTScore（Zhang et al., 2020）用 BERT 向量算**语义相似度**：每个 token 过 BERT 得到向量，然后贪心匹配最相似的 token 对，分别算 Precision、Recall、F1。"喜欢"和"爱"语义接近，所以能拿高分。

## Step 3: 语言模型基础指标——Perplexity 和 Entropy

### 3.1 Perplexity（困惑度）

**语言模型最基础的评测指标**，衡量模型对文本的"惊讶程度"。

$$\text{PPL} = \exp\left(-\frac{1}{N}\sum_{i=1}^{N}\log P(x_i \mid x_{<i})\right) = \exp(\text{Cross-Entropy Loss})$$

直觉：如果模型在每个位置给正确 token 的平均概率是 $p$，那么 $\text{PPL} \approx 1/p$。

```
PPL = 10   → 模型平均在 10 个候选中犹豫 → 好
PPL = 100  → 模型平均在 100 个候选中犹豫 → 差
PPL = 1    → 完美预测每个 token → 不可能

参考值:
  GPT-2 (1.5B) 在 WikiText-103: PPL ≈ 17
  GPT-3 (175B): PPL ≈ 10
  GPT-4 级别: PPL < 8（推测，未公开）
  MiniMind (64M): PPL 会高得多（模型小、词表小）
```

**Perplexity 的限制**：

1. **只能在相同 tokenizer + 相同测试集上对比**。不同 tokenizer 的 PPL 不可比——词表大的 tokenizer 每个位置有更多候选，PPL 天然更高
2. **PPL 低不等于生成质量好**。一个模型可以在 token 级预测很准（PPL 低），但生成的长文本仍然不连贯
3. **PPL 不适用于对话评测**。对话的好坏不在于"下一个 token 有多可预测"

### 3.2 Cross-Entropy Loss vs Output Entropy

这两个名字里都有 entropy，但衡量的是完全不同的东西：

| | 交叉熵 (Cross-Entropy) | 输出熵 (Shannon Entropy) |
|---|---|---|
| 公式 | $H(p, q) = -\sum p_i \log q_i$ | $H(q) = -\sum q_i \log q_i$ |
| 需要标签？ | 需要（$p$ 是 one-hot 标签） | 不需要（只看模型自己的分布 $q$） |
| 衡量什么 | 预测和真值的差距 | 输出分布的分散程度 |
| 值域 | $[0, +\infty)$ | $[0, \log V]$（$V$ = 词表大小） |
| 低值含义 | 预测越准 | 模型越确定（分布集中） |
| 高值含义 | 预测越差 | 模型越犹豫（分布分散） |
| 用途 | 训练 loss | SFT 监控多样性、RL checkpoint 选择 |

```python
import torch.nn.functional as F

logits = model_output.logits[:, -1, :]      # [batch, vocab_size]

# 交叉熵（需要标签）
cross_entropy = F.cross_entropy(logits, labels)

# 输出熵（不需要标签）
probs = F.softmax(logits, dim=-1)
output_entropy = -(probs * probs.log()).sum(dim=-1).mean()
```

**为什么 output entropy 在 SFT→RL 切换中如此重要**：详见 [12-SFT](12-SFT.md) 的"SFT 何时该停 → 切 RL"一节——output entropy 持续下降意味着模型输出越来越同质化，GRPO 的组内 advantage 信号消失（rank inversion）。

### 3.3 Perplexity 和 Cross-Entropy 的关系

$$\text{PPL} = e^{\text{CE}}$$

就是换了个刻度。CE = 2.3 → PPL = $e^{2.3}$ ≈ 10。用 PPL 的好处是直觉更清晰——"模型在 10 个候选里犹豫"比"交叉熵是 2.3"更好理解。

## Step 4: 多样性指标——Distinct-n 和 Self-BLEU

这两个用于衡量模型生成文本的**多样性**，是 SFT 过拟合和 RL 熵坍缩的重要预警信号。

### 4.1 Distinct-n

$$\text{Distinct-n} = \frac{\text{生成文本中不重复的 n-gram 数}}{\text{生成文本中所有 n-gram 数}}$$

```
生成: "我喜欢猫我喜欢狗我喜欢鸟"

所有 1-gram（共 9 个）: [我, 喜欢, 猫, 我, 喜欢, 狗, 我, 喜欢, 鸟]
不重复 1-gram（共 5 个）: {我, 喜欢, 猫, 狗, 鸟}
Distinct-1 = 5/9 = 0.56

所有 2-gram（共 8 个）: [我喜欢, 喜欢猫, 猫我, 我喜欢, 喜欢狗, 狗我, 我喜欢, 喜欢鸟]
不重复 2-gram（共 6 个）: {我喜欢, 喜欢猫, 猫我, 喜欢狗, 狗我, 喜欢鸟}
Distinct-2 = 6/8 = 0.75
```

值低 → 复读机（重复用词），值高 → 词汇丰富。

### 4.2 Self-BLEU

对**同一个 prompt** 生成 N 条回复，计算两两之间的 BLEU：

```
prompt: "介绍一下北京"
生成 5 条回复: [r1, r2, r3, r4, r5]

对 r1: 把 r2, r3, r4, r5 当参考，算 r1 的 BLEU
对 r2: 把 r1, r3, r4, r5 当参考，算 r2 的 BLEU
...
Self-BLEU = 5 条 BLEU 的平均

Self-BLEU 高 → 每条回复和其他回复很像 → 多样性差
Self-BLEU 低 → 每条回复都不一样 → 多样性好
```

注意 Self-BLEU **越低越好**（和普通 BLEU 相反——普通 BLEU 越高说明和参考越像）。

### 4.3 Distinct-n vs Self-BLEU

```
Distinct-n: 衡量单条生成内部的词汇多样性（是不是复读机）
Self-BLEU:  衡量多条生成之间的相似度（同一问题的不同回答是否雷同）

两者互补:
  Distinct-n 高 + Self-BLEU 高 = 每条内部不重复，但条与条之间很像
  Distinct-n 高 + Self-BLEU 低 = 每条都丰富且彼此不同 ← 理想状态
```

## Step 5: 代码与数学推理指标——pass@k

### 5.1 pass@k 的定义

来自 OpenAI Codex 论文（Chen et al., 2021），最初用于代码生成（HumanEval），现在广泛用于数学推理（GSM8K、MATH、AIME）。

**定义：对同一道题采样 k 次，至少有 1 次答对的概率。**

```
pass@1:   采样 1 次，答对的概率 ≈ 单次准确率
pass@10:  采样 10 次，至少 1 次答对的概率 ≈ 能力上限
pass@100: 采样 100 次，至少 1 次答对的概率 ≈ 理论天花板
```

### 5.2 无偏估计器

直接用"k 次里对了几次 / k"来估计 pass@k 是有偏的。Codex 论文给出了无偏估计器：

$$\text{pass@k} = 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}}$$

$n$ = 总采样次数（实践中取 $n = 200$），$c$ = 其中正确的次数，$k$ = 要评估的 k 值。

```
例子: 对一道题采样 200 次，其中 40 次答对 (c=40)

pass@1  = 1 - C(160,1)/C(200,1)  = 1 - 160/200 = 0.20
pass@10 = 1 - C(160,10)/C(200,10) ≈ 0.89
pass@100 ≈ 1.0

解读:
  单次只有 20% 概率答对
  给 10 次机会有 89% 概率答对
  给 100 次机会几乎肯定答对
```

**一次性采 200 次就能同时算 pass@1/10/100**——不需要分别跑三次实验。

### 5.3 pass@1 vs pass@k 的意义

```
pass@1 高 + pass@10 高:  模型既知道怎么做，也总能做对 → 不需要 RL
pass@1 低 + pass@10 高:  模型知道怎么做，但不总做对 → 适合 RL（提升一致性）
pass@1 低 + pass@10 低:  模型不知道怎么做 → 需要更多 SFT 数据或更大模型
```

这就是 [12-SFT](12-SFT.md) 中"SFT 何时切 RL"的判断依据：**RL 不教新知识，只提升已有知识的命中率**。

### 5.4 CodeBLEU

代码专用的 BLEU 变体（Ren et al., 2020），在 n-gram 匹配之外增加了：

```
CodeBLEU = α * BLEU + β * 加权BLEU + γ * AST匹配 + δ * 数据流匹配

AST 匹配: 比较抽象语法树的子树结构
数据流匹配: 比较变量的定义-使用关系

优势: "x = a + b" 和 "x = b + a" 在 CodeBLEU 里接近（语义等价）
     普通 BLEU 可能判定不同
```

## Step 6: LLM Benchmark 套件

Benchmark 是用标准化测试集衡量模型能力的方法。了解主流 benchmark 是面试必备——面试官经常问"你怎么评测模型的 XX 能力"。

### 6.1 知识与推理

| Benchmark | 测什么 | 格式 | 规模 | 典型分数 |
|-----------|--------|------|------|---------|
| **MMLU** | 57 个学科的多选题（高中→研究生级别：物理、历史、法律、医学等） | 4 选 1 | 14,042 题 | GPT-4: ~86%, 开源 70B: ~75% |
| **MMLU-Pro** | MMLU 加难版，选项增加到 10 个，更需要推理 | 10 选 1 | 12,032 题 | 比 MMLU 难 10-20 个点 |
| **ARC** | 小学到初中科学题 | 4 选 1 | 7,787 题 | 分 Easy/Challenge 两个子集 |
| **HellaSwag** | 常识推理：选最合理的故事续写 | 4 选 1 | 10,042 题 | GPT-4: ~95% |
| **WinoGrande** | 代词消歧，需要常识推理 | 2 选 1 | 1,267 题 | "他把奖杯放进箱子里因为它太大了"——"它"指谁？ |
| **TruthfulQA** | 模型会不会输出常见误解（"长城从月球能看到吗"） | 多选/生成 | 817 题 | 测的是"不编造"的能力 |

**MMLU 是最常被引用的知识 benchmark**——几乎所有模型发布的论文都会报 MMLU 分数。

### 6.2 数学

| Benchmark | 测什么 | 难度 | 典型分数 |
|-----------|--------|------|---------|
| **GSM8K** | 小学数学应用题（加减乘除、简单方程） | 入门 | GPT-4: ~95%, 7B 模型: ~50-70% |
| **MATH** | 竞赛级数学（代数/几何/数论/概率） | 困难 | GPT-4: ~50-70%, 7B: ~20-30% |
| **AIME** | 美国数学邀请赛真题 | 极难 | DeepSeek-R1: ~70%+, 一般模型 < 30% |

**GSM8K 是数学能力的入门门槛**——如果模型连小学应用题都做不好，数学推理基本不可用。

### 6.3 代码

| Benchmark | 测什么 | 规模 | 典型分数 |
|-----------|--------|------|---------|
| **HumanEval** | 函数级代码生成（给 docstring 写 Python 实现） | 164 题 | GPT-4: ~90%+ pass@1 |
| **HumanEval+** | HumanEval 加强版（更多测试用例，减少假阳性） | 164 题 | 比原版低 5-15 个点 |
| **MBPP** | 简单编程题（Mostly Basic Python Programs） | 974 题 | 题目简单但量大 |
| **SWE-bench** | 真实 GitHub issue 修复（给 issue 描述 + 仓库代码，生成 patch） | 2,294 题 | Claude/GPT 系: ~50%, 开源: ~20-30% |
| **LiveCodeBench** | 持续更新的竞赛编程题 | 动态 | 防数据污染——题目来自最新竞赛 |

**SWE-bench 是目前最接近"真实编程能力"的 benchmark**——不是写算法题，而是修真实 bug。

### 6.4 指令跟随

| Benchmark | 测什么 | 方法 |
|-----------|--------|------|
| **IFEval** | 严格遵循格式指令（"用 JSON 回答""不超过 100 字""必须包含以下关键词"） | 规则检查，无需模型评判 |
| **MT-Bench** | 多轮对话质量（写作、推理、编程、数学等 8 个类别） | GPT-4 打分 1-10 |
| **AlpacaEval** | 单轮指令跟随，和参考模型（GPT-4）对比 | GPT-4 判断 win/lose |

**IFEval 是 SFT 质量的最直接衡量**——模型是否真的学会了"听指令"。在 [12-SFT](12-SFT.md) 的 checkpoint 选择中，IFEval 达标是"格式门槛"。

### 6.5 综合排行榜

| 排行榜 | 方法 | 特点 |
|--------|------|------|
| **Chatbot Arena (LMSYS)** | 真人盲评 AB 对比 → ELO 评分 | 最贴近"人觉得哪个好"，业界公认最权威 |
| **Open LLM Leaderboard** | HuggingFace 上的标准化 benchmark 集合 | 开源模型排名的事实标准 |
| **LiveBench** | 持续更新题目，从最新来源采集 | 防数据污染，每月刷新 |
| **SEAL Leaderboards** | 多维度评测（安全、编码、指令跟随等） | Scale AI 维护 |

### 6.6 Benchmark 的局限性

1. **数据污染（Data Contamination）**：如果 benchmark 的题目出现在训练数据中，分数虚高。这就是 LiveBench/LiveCodeBench 要持续更新题目的原因
2. **Benchmark 饱和**：HellaSwag 已经被刷到 95%+ ，区分度消失
3. **和真实使用体验脱节**：MMLU 高不代表用户觉得好用——Chatbot Arena 的 ELO 和 MMLU 的相关性并不完美
4. **过度优化（Goodhart 定律）**：当 benchmark 变成优化目标，它就不再是好的衡量标准。模型可能在 MMLU 上刷分但实际能力没提升

## Step 7: 对齐与偏好指标

### 7.1 Win Rate（胜率）

两个模型对同一 prompt 生成回复，由人类或 GPT-4 判断哪个更好：

```
100 个 prompt:
  模型 A 赢 60 次，模型 B 赢 35 次，平 5 次
  A 的 win rate = 60%

AlpacaEval 的 LC win rate（length-controlled）:
  修正了"更长的回复容易被判更好"的偏差
  → 用回归模型控制长度变量后再算胜率
```

### 7.2 ELO Rating

来自国际象棋的评分系统，Chatbot Arena 用它给模型排名。

```
原理: 每次人类 AB 对比相当于一局棋
  A 赢 → A 的 ELO 升，B 的 ELO 降
  升降幅度取决于"意外程度":
    弱胜强 → 升得多（爆冷）
    强胜弱 → 升得少（正常）

ELO 差距的含义:
  差 100 分 → 强者胜率约 64%
  差 200 分 → 强者胜率约 76%
  差 400 分 → 强者胜率约 91%

2025-2026 参考值:
  GPT-4o / Claude 3.5 Sonnet: ELO ≈ 1280+
  开源最强 (LLaMA 3 405B): ELO ≈ 1200+
  7B 级开源模型: ELO ≈ 1050-1100
```

### 7.3 Reward Model Score

RLHF 的核心组件——用 reward model 给回复打分：

```
prompt + response → Reward Model → 标量分数（越高越好）

用途:
  1. RLHF/PPO 训练时提供 reward 信号
  2. Best-of-N 采样: 生成 N 条回复，选 reward 最高的
  3. 模型评测: 对比不同 checkpoint 的平均 reward

注意: Reward model 可能被 hack（模型学会讨好 RM 而不是真正变好）
      → 需要 gold reward model 或人类评估做校验
```

### 7.4 KL Divergence

RL 阶段的核心监控指标，衡量训练中的模型（policy）和基线模型（reference）的分布差距：

$$D_{KL}(\pi \| \pi_{\text{ref}}) = \mathbb{E}_{\pi}\left[\log \frac{\pi(a|s)}{\pi_{\text{ref}}(a|s)}\right]$$

```
KL 太大 → 模型偏离基线太远
  → 可能出现 reward hacking（学会讨好 RM 的技巧，如加很多"当然"、"好的"）
  → 可能丧失预训练学到的基础能力

KL 太小 → RL 几乎没改变模型
  → reward 信号太弱或学习率太低

PPO/DPO/GRPO 都有 KL 约束:
  PPO: 在 reward 中减去 β * KL 作为惩罚项
  DPO: 隐式通过 β 参数控制偏离程度
  GRPO: KL 惩罚项直接加在 loss 中
```

## Step 8: 效率指标

模型不只要"好"，还要"快"和"省"。效率指标在部署和推理优化中至关重要。

| 指标 | 全称 | 含义 | 典型值 |
|------|------|------|--------|
| **TTFT** | Time To First Token | 发送请求到收到第一个 token 的延迟 | 100ms ~ 2s |
| **TPS** | Tokens Per Second | 生成阶段每秒输出的 token 数 | 30-100 tps |
| **Throughput** | — | 系统级每秒处理的总 token 数（含并发） | 取决于硬件和批大小 |
| **FLOPs** | Floating Point Operations | 训练/推理的浮点运算总量 | GPT-4 训练约 $2 \times 10^{25}$ FLOPs（推测） |
| **MFU** | Model FLOPs Utilization | 实际算力 / GPU 理论峰值算力 | 好的框架: 40-60% |

```
TTFT vs TPS 的区别:

用户发送请求 ──→ [等待 TTFT] ──→ 第一个 token ──→ [TPS 速率输出] ──→ 最后一个 token
                   ↑ 用户感知的延迟                    ↑ 用户感知的流畅度

TTFT 主要取决于 prefill 阶段（处理输入 prompt）
TPS 主要取决于 decode 阶段（自回归生成）

长 prompt + 短回复: TTFT 占比大
短 prompt + 长回复: TPS 占比大
```

**MFU 是衡量训练框架效率的黄金指标**：

```
理论: A100 BF16 峰值 = 312 TFLOPS
实际: 你的训练每秒实际做了 150 TFLOPS 的有效计算
MFU = 150 / 312 = 48%

MFU 低的原因:
  1. 通信开销（多卡同步）
  2. 显存搬运（带宽瓶颈）
  3. 气泡（pipeline 并行的空闲时间）
  4. 代码实现效率

MiniMind 单卡训练不涉及多卡通信，MFU 主要受显存带宽限制
```

## Step 9: 数据质量指标

| 指标 | 用途 | 方法 |
|------|------|------|
| **Contamination rate** | 检测 benchmark 数据是否泄露到训练集 | 用 n-gram 或嵌入相似度匹配训练数据和测试集 |
| **Dedup ratio** | 训练数据的去重比例 | MinHash / SimHash 去重后保留的比例 |
| **Toxicity score** | 文本的毒性程度 | Perspective API 打分 0-1 |
| **Data quality score** | 训练数据的质量评分 | 用强模型（GPT-4）给每条数据打分，筛选高质量子集 |
| **Truncation rate** | 因超 max_length 被截断的样本比例 | 训练前统计，>1% 就需要处理 |

## 易混淆对照表

| 对比 | 区别 |
|------|------|
| **BLEU vs ROUGE** | BLEU = precision 导向（翻译），ROUGE = recall 导向（摘要） |
| **Perplexity vs Cross-Entropy** | PPL = exp(CE)，同一个东西换了刻度 |
| **Output Entropy vs Cross-Entropy** | Output entropy 不需标签（衡量多样性），CE 需要标签（衡量准确性） |
| **pass@1 vs Accuracy** | pass@1 通常指采样（temperature > 0），Accuracy 通常指 greedy 解码 |
| **BLEU vs Self-BLEU** | BLEU: 生成 vs 参考 → 越高越好；Self-BLEU: 生成 vs 生成 → 越低越好 |
| **F1 (分类) vs F1 (QA)** | 分类 F1: 实体/类别级；QA F1: token 级（答案 span 共享 token） |
| **Win Rate vs ELO** | Win rate: 两两对比的胜率；ELO: 从大量对比中算出的绝对分数，可排名 |
| **Reward vs KL** | Reward 越高越好（模型回复质量），KL 要控制在合理范围（不能太偏离基线） |
| **Distinct-n vs Self-BLEU** | Distinct-n: 单条内部的词汇多样性；Self-BLEU: 多条之间的相似度 |
| **TTFT vs TPS** | TTFT: 用户等多久才看到第一个字；TPS: 之后每秒蹦出几个字 |

## 面试话术

> "评测指标我按阶段理解。预训练主要看 perplexity——它就是交叉熵 loss 取 exp，
> 直觉上是模型在多少个候选 token 里犹豫。但 PPL 只能在相同 tokenizer 和测试集上对比。
>
> SFT 阶段 train loss 意义不大——数据量小模型一定能背下来。我更关注 eval loss（过拟合信号）、
> token accuracy、output entropy（多样性预警）和 EOS 结束率（模型能不能正确停止）。
> 特别是如果后面要接 RL，选 checkpoint 不应该选 eval loss 最低的，
> 而是在通过格式门槛后选 output entropy 最高的——因为 rank inversion。
>
> RL 阶段最重要的是 reward 和 KL divergence。KL 太大说明模型偏离基线太远，
> 可能在 reward hack；KL 太小说明 RL 没学到东西。pass@k 用来判断该不该切 RL——
> pass@10 高但 pass@1 低说明模型知道怎么做但不总做对，这正好是 RL 能解决的。
>
> 发布时看的是 benchmark 套件——MMLU 测知识、GSM8K 测数学、HumanEval 测代码、
> MT-Bench 测对话、Arena ELO 是真人盲评排名。但 benchmark 有数据污染问题，
> 所以 LiveBench 这种持续更新的越来越重要。
>
> 传统指标里 BLEU 是 precision 导向用于翻译，ROUGE 是 recall 导向用于摘要，
> 但在 LLM 时代这两个用得越来越少——BERTScore 用语义相似度替代表面匹配，
> 而最权威的还是 Arena 的真人 ELO。"
