## Part 1: 一张卡为什么不够

### 1.1 存不下：7B 模型的显存账单

训练一个模型，显存里要装四样东西。用 7B 参数、AdamW 优化器、BF16 混合精度来算：

| 项目 | 每个参数占多少字节 | 7B 模型总量 |
|------|-----------------|-----------|
| **模型参数**（FP32 master weights） | 4 B | 28 GB |
| **BF16 参数副本**（前向/反向用） | 2 B | 14 GB |
| **梯度**（BF16） | 2 B | 14 GB |
| **AdamW 状态**（m + v，FP32） | 4 + 4 = 8 B | 56 GB |
| **合计（模型状态）** | **16 B** | **112 GB** |

> 算法：7B × 16 字节 = 112 GB。这还**没算激活值**——前向传播的中间结果。

一张 A100 有 80 GB 显存。112 GB 的模型状态都装不下，更别提还要留空间给激活值。

如果是 70B 模型：70B × 16 = 1120 GB = 1.1 TB，需要 14 张 A100 才放得下模型状态。

### 1.2 算不完：1T token 要训多久

即使显存够用，训练速度也是问题。粗略估算训练所需时间：

$$\text{训练时间(秒)} \approx \frac{6 \times N \times D}{\text{GPU 算力} \times \text{MFU}}$$

- $N$ = 参数量，$D$ = token 数
- 因子 6：每个 token 需要约 6 次浮点运算（前向 2 + 反向 4）
- MFU（Model FLOPs Utilization）：GPU 算力的实际利用率，通常约 30%-50%

代入 7B 模型 + 1T token + 1 张 A100（312 TFLOPS BF16）+ 40% MFU：

```
时间 = 6 × 7e9 × 1e12 / (312e12 × 0.4)
     = 4.2e22 / 1.25e14
     = 3.36e8 秒
     ≈ 3889 天
     ≈ 10.6 年
```

一张卡训 7B 要 10 年。用 8 张 A100 并行：10.6 / 8 ≈ 1.3 年。用 64 张：~60 天。用 256 张：~15 天。

**结论**：大模型训练有两个必须解决的问题——**存不下**和**算不完**。本章的所有技术，都是在解决其中之一或两者兼顾。

### 1.3 本章路线图

```
问题: 一张卡存不下 + 算不完
  │
  ├─ Part 2: DDP（数据并行）
  │    每卡一份完整模型，各看不同数据 → 加速 N 倍
  │    问题: 每卡都存一份完整模型 = N 倍显存浪费
  │
  ├─ Part 3: ZeRO / FSDP
  │    切掉冗余的优化器状态/梯度/参数 → 显存降到 1/N
  │    问题: 70B 模型一层就超过单卡显存
  │
  ├─ Part 4: TP + PP（模型并行）
  │    TP: 一层模型切到多卡
  │    PP: 不同层放不同卡
  │
  └─ Part 5: 组合策略
       DP + TP + PP = 3D 并行
       面试真题 + 业界实例
```

## Part 2: 数据并行——从 DP 到 DDP

### 2.1 最朴素的想法：DP（DataParallel）

一张卡算不完，最直觉的想法是：**把数据分给多张卡，各自算梯度，汇总后更新参数**。PyTorch 最早的方案 `nn.DataParallel`（简称 DP）就是这么做的——单进程多线程，指定一张"主卡"（通常是 GPU 0）来协调一切。

**DP 每个 step 的流程**：

```
Step 开始
  │
  ├─ 1. Scatter 数据：GPU 0 把一个 batch 切成 4 份，分发给 4 张卡
  │
  ├─ 2. Broadcast 模型：GPU 0 把最新的参数广播给其他卡
  │     （因为只有 GPU 0 更新了参数，其他卡的参数是过期的）
  │
  ├─ 3. 各卡独立做前向 + 反向，算出各自的梯度
  │
  ├─ 4. Gather 梯度：所有卡把梯度传回 GPU 0
  │
  ├─ 5. GPU 0 汇总梯度（求平均），执行 optimizer.step() 更新参数
  │
  └─ 回到 Step 1，GPU 0 再次 Broadcast 新参数
```

代码很简单——一行 `model = nn.DataParallel(model)` 就行。但 DP 有**三个致命问题**：

**问题一：GPU 0 是通信瓶颈。** 每个 step 的 Broadcast 参数和 Gather 梯度都以 GPU 0 为中心（星型拓扑）。GPU 越多，GPU 0 的通信量线性增长，其他卡全在干等。

```
DP 的星型通信:
            GPU 1
           ↗     ↘
  GPU 0 ← ─ ─ ─ → GPU 2     所有流量都经过 GPU 0
           ↘     ↗
            GPU 3
```

**问题二：Python GIL 限制并行。** DP 是单进程多线程。Python 的全局解释器锁（GIL）导致多线程无法真正并行执行 Python 代码，吞吐量上不去。

**问题三：显存不均衡。** GPU 0 要额外存汇总后的梯度，比其他卡多占一块显存。卡越多，GPU 0 越先 OOM。

> DP 现在已经**没人用了**——PyTorch 官方文档都建议直接用 DDP。但理解 DP 的问题，才能理解 DDP 每个设计决策的动机。

### 2.2 DDP：去掉主卡，对等通信

DDP（Distributed Data Parallel）解决了 DP 的所有问题。核心改变：**没有主卡，每张卡都是对等的，各自持有完整模型和优化器，各自独立更新参数**。

```
         数据集: [batch_0, batch_1, batch_2, batch_3, ...]
                    ↓         ↓         ↓         ↓
DDP:     GPU 0 看 batch_0   GPU 1 看 batch_1   GPU 2 看 batch_2   GPU 3 看 batch_3
         (完整模型)          (完整模型)          (完整模型)          (完整模型)
            ↓                  ↓                  ↓                  ↓
         各自算梯度 g_0       g_1                g_2                g_3
            ↓                  ↓                  ↓                  ↓
         ──────────── AllReduce: 求平均 ────────────
            ↓                  ↓                  ↓                  ↓
         每卡都得到 ḡ = (g_0 + g_1 + g_2 + g_3) / 4
            ↓                  ↓                  ↓                  ↓
         各自用 ḡ 更新参数 → 四张卡的参数保持一致
```

关键区别：每张卡都有自己的 optimizer，AllReduce 后各自独立更新参数。因为拿到的平均梯度完全相同，更新后的参数也自然一致——不需要任何卡去"通知"其他卡新参数是什么。

**DP → DDP 解决了什么**：

| | DP | DDP |
|--|-----|------|
| **架构** | 单进程多线程，GPU 0 当主卡 | 多进程，无主卡，对等通信 |
| **梯度同步** | Gather 到主卡求和再 Broadcast（星型） | AllReduce 对等交换（环型） |
| **参数更新** | 只有 GPU 0 更新，再 Broadcast 给副卡 | 每卡各自更新，天然一致 |
| **GIL** | 受限（单进程多线程） | 不受限（多进程） |
| **显存均衡** | GPU 0 额外存梯度汇总，容易 OOM | 各卡显存占用一致 |

效果：4 张卡同时训练，每个 step 处理 4 倍的数据 → **训练速度接近线性加速**（通信开销除外）。

数学上，DDP 等价于用 4 倍大的 batch size 在单卡上训练——因为梯度是 4 个 mini-batch 的平均。

### 2.3 梯度怎么同步：AllReduce

DDP 的核心操作是 **AllReduce**：让所有卡上的梯度求和（或求平均），结果广播到每张卡。

```
AllReduce 前:                    AllReduce 后:
  GPU 0: g_0 = [1.0, 2.0]         GPU 0: ḡ = [2.5, 3.5]
  GPU 1: g_1 = [3.0, 4.0]         GPU 1: ḡ = [2.5, 3.5]
  GPU 2: g_2 = [2.0, 5.0]         GPU 2: ḡ = [2.5, 3.5]
  GPU 3: g_3 = [4.0, 3.0]         GPU 3: ḡ = [2.5, 3.5]

  操作: sum 再 /4 → 每张卡都拿到相同的平均梯度
```

AllReduce 结束后，每张卡用同样的梯度 ḡ 做同样的参数更新 → 参数保持同步。

**但 AllReduce 怎么实现？** 最朴素的方法就是 2.1 DP 的做法——所有卡把梯度 Gather 到主卡，主卡求和后再 Broadcast 出去。但主卡的通信量是 $O(N \times P)$（$P$ = 参数量），正是 DP 的瓶颈所在。DDP 实际用的是 **Ring-AllReduce**。

### 2.4 补充：集合通信原语

在讲 Ring-AllReduce 之前，先认识 6 种基本的多卡通信操作。后面 ZeRO 和 TP 也会反复用到它们。

```
Broadcast:      一张卡的数据 → 发给所有卡
                GPU 0: [A]  →  GPU 0: [A],  GPU 1: [A],  GPU 2: [A],  GPU 3: [A]

Scatter:        一张卡的数据 → 拆开分给各卡
                GPU 0: [A,B,C,D]  →  GPU 0: [A],  GPU 1: [B],  GPU 2: [C],  GPU 3: [D]

Gather:         各卡的数据 → 收集到一张卡
                GPU 0: [A], GPU 1: [B], GPU 2: [C], GPU 3: [D]  →  GPU 0: [A,B,C,D]

AllGather:      各卡的数据 → 收集后每张卡都拿到完整的
                GPU 0: [A], GPU 1: [B], GPU 2: [C], GPU 3: [D]
                → 每卡都变成 [A,B,C,D]

ReduceScatter:  各卡的数据 → 先求和，再拆开分给各卡
                GPU 0: [a0,a1,a2,a3]
                GPU 1: [b0,b1,b2,b3]
                GPU 2: [c0,c1,c2,c3]
                GPU 3: [d0,d1,d2,d3]
                → GPU 0: [a0+b0+c0+d0], GPU 1: [a1+b1+c1+d1], ...

AllReduce:      各卡的数据 → 求和后每张卡都拿到完整结果
                = ReduceScatter + AllGather
```

**记忆方法**：名字里带 "All" = 每张卡都拿到结果。Reduce = 求和。Scatter = 拆分。Gather = 收集。

**后面哪里会用到**：
- **DDP**：AllReduce 同步梯度
- **ZeRO-3 / FSDP**：前向时 AllGather 取回参数，反向时 ReduceScatter 拆分梯度
- **TP**：前向/反向各做一次 AllReduce

### 2.5 Ring-AllReduce：通信量和卡数无关

Ring-AllReduce 是 AllReduce 的高效实现。核心思想：把 $N$ 张卡排成一个环，数据分成 $N$ 块，沿环传递——每张卡只和相邻两张卡通信。

分两个阶段：

**阶段 1：ReduceScatter（环上传 N-1 轮，每轮发 1/N 的数据）**

```
4 张卡排成环，梯度分成 4 块: [块0, 块1, 块2, 块3]

第 1 轮: 每卡把自己的一块发给下一张卡
  GPU 0 → GPU 1: 块0    GPU 1 → GPU 2: 块1    GPU 2 → GPU 3: 块2    GPU 3 → GPU 0: 块3
  收到后和自己的对应块求和

第 2 轮: 把刚求完和的块继续发给下一张卡
  ...再求和

第 3 轮: 同理

3 轮后: 每卡持有一块的完整求和结果
  GPU 0 有 块3 的完整和，GPU 1 有 块0 的完整和，...
```

**阶段 2：AllGather（环上再传 N-1 轮，把求和结果广播给所有卡）**

3 轮后：每张卡都拥有所有块的完整求和 → AllReduce 完成。

**关键：通信量和卡数无关。**

每张卡在每轮发送 $P/N$ 大小的数据（$P$ = 参数量），共 $2(N-1)$ 轮。每张卡的总发送量：

$$\text{每卡通信量} = 2 \times (N-1) \times \frac{P}{N} = 2P \times \frac{N-1}{N} \approx 2P$$

当 $N$ 较大时，$\frac{N-1}{N} \approx 1$，每卡通信量趋近于 $2P$——和卡数无关。这就是 Ring-AllReduce 可以线性扩展的原因。

用 7B 模型、BF16 梯度举例：$P$ = 7B × 2 字节 = 14 GB。每卡通信量 ≈ 28 GB。在 NVLink 带宽（~600 GB/s 双向）下，通信耗时约 28/600 ≈ 0.047 秒——远小于一步训练的计算时间。

### 2.6 MiniMind 的 DDP 代码

MiniMind 在 `scratch/trainer/train_pretrain.py` 中实现了完整的 DDP 支持。一共 5 步，每步只加几行代码：

> 📁 以下代码已经写在 `scratch/trainer/train_pretrain.py` 和 `scratch/trainer/trainer_utils.py` 中

**Step 1：初始化分布式环境**

`torchrun` 启动时自动设置环境变量 `RANK`（全局编号）、`LOCAL_RANK`（本机编号）、`WORLD_SIZE`（总卡数）。`init_distributed_mode()` 读取这些变量，初始化 NCCL 通信后端：

```python
# trainer_utils.py
def init_distributed_mode():
    if int(os.environ.get("RANK", -1)) == -1:
        return 0  # 非 DDP 模式，直接返回

    dist.init_process_group(backend="nccl")      # 初始化通信后端
    local_rank = int(os.environ["LOCAL_RANK"])    # 本机第几张卡
    torch.cuda.set_device(local_rank)             # 绑定 GPU
    return local_rank
```

启动命令从 `python train.py` 变成 `torchrun --nproc_per_node=4 train.py`，torchrun 自动启动 4 个进程。

**Step 2：DistributedSampler 切分数据**

```python
# train_pretrain.py
train_sampler = DistributedSampler(train_ds) if dist.is_initialized() else None
loader = DataLoader(train_ds, batch_size=args.batch_size,
                    shuffle=(train_sampler is None),  # 有 sampler 时 shuffle 由 sampler 管
                    sampler=train_sampler)
```

DistributedSampler 把数据集按 rank 均匀切分：4 张卡时，每卡只看 1/4 的数据。

**Step 3：用 DDP 包装模型**

```python
if dist.is_initialized():
    model = DistributedDataParallel(model, device_ids=[local_rank])
```

一行代码。DDP 的 hook 自动在 `loss.backward()` 时做 AllReduce——用 **Gradient Bucket** 机制把小梯度攒成大块一起通信，和反向传播重叠执行，减少等待时间。

**Step 4：每 epoch 更新 sampler 种子**

```python
if train_sampler is not None:
    train_sampler.set_epoch(epoch)
```

不调 `set_epoch` 的话，每个 epoch 各卡拿到的数据切分方式相同——模型反复看同样的 batch 组合。

**Step 5：只在 rank 0 保存和打印**

```python
if is_main_process():       # rank == 0
    torch.save(model.module.state_dict(), ckp)    # .module 拿到原始模型
```

4 张卡的模型参数完全一样（AllReduce 保证的），只需要存一份。打印日志也一样——不加这个判断就会打 4 遍。

### 2.7 DDP 的限制

DDP 解决了"算不完"的问题——$N$ 张卡加速约 $N$ 倍。但它没有解决"存不下"：

```
DDP: 4 张 A100，每张 80 GB

  GPU 0: 完整模型(112 GB) + 激活值    ← 存不下！
  GPU 1: 完整模型(112 GB) + 激活值    ← 同上
  GPU 2: 完整模型(112 GB) + 激活值
  GPU 3: 完整模型(112 GB) + 激活值

  4 张卡总共存了 4 份一模一样的模型状态 = 448 GB
  其中 336 GB 是冗余的（只有 1 份是必要的）
```

**问题**：每张卡都存完整的 112 GB 模型状态，4 张卡就有 3 份冗余。能不能切开来，每卡只存 1/4？这就是 ZeRO 要做的事。

## Part 3: ZeRO——切掉冗余

> **通信原语速查**（详见 2.4）：
> - **ReduceScatter**：各卡的数据求和后，结果分散到各卡（每卡只拿 1/N）。通信量 ≈ P
> - **AllGather**：每卡发出自己的那份，所有卡拼出完整数据。通信量 ≈ P
> - **AllReduce** = ReduceScatter + AllGather，通信量 ≈ 2P。这是 DDP 同步梯度的方式，也是本章的通信量基准（1×）

### 3.1 DDP 的浪费有多大

回顾 1.1 的显存账单——7B 模型的 112 GB 模型状态由三部分组成：

```
模型状态 = 参数(14 GB) + 梯度(14 GB) + 优化器状态(84 GB)
                                        ↑
                                     AdamW 的 m + v + FP32 master weights
                                     = (4+4+4) × 7B = 84 GB
```

> 注：1.1 把参数拆成了 FP32(28GB) + BF16(14GB)，这里按 ZeRO 论文的惯例把 FP32 master weights 算在优化器状态里——总量不变，只是归类不同。

DDP 下 8 张 A100：

```
每卡:  参数 14 GB + 梯度 14 GB + 优化器 84 GB = 112 GB
8 卡:  112 × 8 = 896 GB
实际需要: 112 GB（只需一份）
冗余: 896 - 112 = 784 GB（87%）
```

ZeRO（**Ze**ro **R**edundancy **O**ptimizer，Rajbhandari et al., 2020）的思路很简单：这三样东西在训练的不同阶段才用到，不需要每张卡都存完整的一份。按"需要时取、用完即丢"的原则，分三个阶段逐步切分。

### 3.2 ZeRO-1：切分优化器状态

优化器状态（AdamW 的 m、v、FP32 master weights）占了 84 GB / 112 GB ≈ 75% 的模型状态——是最大的一块。

ZeRO-1 的做法：把优化器状态均匀切成 $N$ 份，每卡只存 $1/N$。

**每卡永久存什么**（理解通信的前提）：

```
DDP 每卡持有:                          ZeRO-1 每卡持有:
  参数(BF16):    完整 14 GB              参数(BF16):    完整 14 GB  ← 没变
  梯度(BF16):    完整 14 GB              梯度(BF16):    完整 14 GB  ← 没变
  optimizer:     完整 84 GB              optimizer:     只有 1/8 = 10.5 GB  ← 切了
  每卡: 112 GB                           每卡: 14 + 14 + 10.5 = 38.5 GB ✓
```

> optimizer 状态包括三样东西（见 1.1）：FP32 master weights + Adam 的 m + Adam 的 v。参数更新在 FP32 精度下进行，算完再转回 BF16 写回工作副本。

**一个训练 step 的完整流程**：

```
1. 前向传播
   BF16 参数完整在本地 → 正常算，不需要通信                          ← 0

2. 反向传播
   BF16 参数完整在本地 → 正常算梯度，不需要通信                       ← 0

3. AllReduce 梯度
   每卡反向后有一份 BF16 梯度，需要和其他卡的梯度求平均
   → ReduceScatter：各卡梯度求和，每卡拿到 1/N 的求和梯度            ← 通信 P
   → AllGather：把各卡的 1/N 拼回来，每卡拿到完整的求和梯度           ← 通信 P
   （ZeRO-1 没有优化梯度同步，和 DDP 一样做完整 AllReduce）

4. 更新参数（每卡只更新自己负责的 1/N）
   GPU 0 拿第 0 份梯度（BF16 → 转成 FP32）+ 第 0 份 Adam m, v
     → Adam 公式在 FP32 精度下更新第 0 份 FP32 master weights（源头）
     → 把更新后的 FP32 master weights 截断为 BF16 → 写回 BF16 工作副本

   GPU 0 的第 1~7 份参数？没有对应的 optimizer，更新不了，还是旧的

5. AllGather 更新后的 BF16 参数
   每卡把自己刚更新的那 1/N BF16 参数发出去
   → 所有卡拼回完整的、最新的 BF16 参数                              ← 通信 P
   （DDP 不需要这步——DDP 每卡有完整 optimizer，各自更新全部参数，天然一致）

合计 = P + P + P = 3P = 1.5× DDP
多出的 P（第 5 步）换来了 optimizer 从 84 GB 降到 10.5 GB。
```

### 3.3 ZeRO-2：再切梯度

ZeRO-1 之后，梯度（14 GB）仍然每卡存一份完整的。但仔细想——第 3 步 AllReduce 给了每卡完整梯度，可第 4 步每卡只更新 1/N 参数，其余 7/8 的梯度拿到了也用不上，白搬了。

ZeRO-2 的做法：梯度不再 AllReduce（每卡拿到完整梯度），而是只做 **ReduceScatter**（每卡只拿到自己负责的 1/N 梯度）。拿不到的 7/8 梯度？反正用不上，直接丢掉。

**每卡永久存什么**：

```
ZeRO-1 每卡持有:                        ZeRO-2 每卡持有:
  参数(BF16):    完整 14 GB               参数(BF16):    完整 14 GB   ← 没变
  梯度(BF16):    完整 14 GB               梯度(BF16):    只有 1/8 = 1.75 GB  ← 切了
  optimizer:     1/8 = 10.5 GB            optimizer:     1/8 = 10.5 GB  ← 没变
  每卡: 38.5 GB                           每卡: 14 + 1.75 + 10.5 = 26.25 GB ✓
```

**一个训练 step 的完整流程**：

```
1. 前向传播
   BF16 参数完整在本地 → 正常算，不需要通信                          ← 0

2. 反向传播
   BF16 参数完整在本地 → 正常算梯度，不需要通信                       ← 0

3. ReduceScatter 梯度（和 ZeRO-1 的关键区别在这里）
   每卡反向后有一份完整梯度，但只需要自己负责的 1/N
   → ReduceScatter：各卡的梯度求和，每卡只拿到自己负责的那 1/N       ← 通信 P
   不做 AllGather——其他 7/8 的梯度对自己没用，不搬了               ← 省了 P！

4. 更新参数（和 ZeRO-1 完全一样）
   GPU 0 拿第 0 份梯度（BF16 → 转成 FP32）+ 第 0 份 Adam m, v
     → Adam 公式在 FP32 精度下更新第 0 份 FP32 master weights（源头）
     → 把更新后的 FP32 master weights 截断为 BF16 → 写回 BF16 工作副本

5. AllGather 更新后的 BF16 参数（和 ZeRO-1 完全一样）
   每卡把自己刚更新的那 1/N BF16 参数发出去
   → 所有卡拼回完整的、最新的 BF16 参数                             ← 通信 P

合计 = P + P = 2P = 1× DDP
```

**和 ZeRO-1 对比，省在哪**：

```
ZeRO-1:  第 3 步 AllReduce(2P) + 第 5 步 AllGather 参数(P) = 3P
ZeRO-2:  第 3 步 ReduceScatter(P) + 第 5 步 AllGather 参数(P) = 2P
                 ↑
         第 3 步砍掉了 AllGather 梯度（P），省了一次搬运
         第 4、5 步和 ZeRO-1 完全一样

总通信量和 DDP 相同（2P）——但显存又降了。
```

### 3.4 ZeRO-3：连参数也切

ZeRO-2 的参数（14 GB）仍然每卡存一份完整的。但参数也只在前向和反向时才用到——用完可以丢掉，需要时再从其他卡取回来。

ZeRO-3 的做法：参数也均匀切成 $N$ 份，每卡只永久存自己负责的 1/N。

**每卡永久存什么**：

```
ZeRO-3 每卡永久持有:
  参数:      只有 1/8 = 1.75 GB    ← 关键变化：参数不完整了！
  梯度:      只有 1/8 = 1.75 GB
  optimizer: 只有 1/8 = 10.5 GB
  每卡合计:  1.75 + 1.75 + 10.5 = 14 GB ✓
```

显存从 112 GB 降到 14 GB——8 张卡把 112 GB 平摊了。

**但参数不完整意味着：前向和反向都跑不了**。要算某一层，这层的参数散落在 8 张卡上，必须临时取回来。

**一个训练 step 的完整流程**：

```
1. 前向第 L 层
   BF16 参数不在本地（只存了 1/N）
   → AllGather 从 8 张卡取回第 L 层完整 BF16 参数
   → 用完整参数算前向
   → 立即释放这层参数（不释放就和 ZeRO-2 一样占满显存了，白切了）

   前向第 L+1 层：同理，AllGather → 算 → 释放
   ...所有层走完
   所有层的参数加起来 AllGather 了一遍完整模型                    ← 通信 P

2. 反向第 L 层
   参数又不在了（前向时已经释放了）
   → AllGather 再次取回第 L 层完整 BF16 参数
   → 用完整参数算梯度
   → 释放参数

   反向第 L-1 层：同理
   ...所有层走完
   所有层的参数又 AllGather 了一遍完整模型                        ← 通信 P

3. ReduceScatter 梯度
   和 ZeRO-2 一样，每卡只拿自己负责的 1/N 梯度                   ← 通信 P

4. 更新参数（和 ZeRO-2 的第 4 步完全一样）
   GPU 0 拿第 0 份梯度（BF16 → 转成 FP32）+ 第 0 份 Adam m, v
     → Adam 公式在 FP32 精度下更新第 0 份 FP32 master weights（源头）
     → 把更新后的 FP32 master weights 截断为 BF16 → 写回 BF16 工作副本
   （不需要 AllGather 参数——反正每卡只永久存 1/N，下次前向时再取）

合计 = P + P + P = 3P = 1.5× DDP
```

**ZeRO-3 vs ZeRO-2，多出的 P 是什么**：

```
                 参数完整在本地吗？    前向/反向需要取参数吗？     AllGather 参数几次？
ZeRO-2:   完整参数常驻显存          不需要，直接用              1 次（更新后同步）
ZeRO-3:   只存 1/N                 每次都要取                  2 次（前向取+反向取）

ZeRO-2: ReduceScatter 梯度(P) + AllGather 参数(P)                = 2P
ZeRO-3: AllGather 参数(P) + AllGather 参数(P) + ReduceScatter 梯度(P) = 3P
                                    ↑
                      多出来的这个 P = 反向时再取一次参数
                      （前向取完释放了，反向时参数已不在）
```

ZeRO-3 是用通信时间换显存空间——通信量比 ZeRO-2 多了 P，但显存从 26.25 GB 降到 14 GB。

### 3.5 ZeRO 三阶段对比

四种方案的完整工作流程对比（带通信标注）：

```
           参数在本地？  前向/反向通信   梯度同步         更新后同步         合计

DDP:       ✅ 完整      无需通信        AllReduce(2P)    不需要（各自更新全部）  2P

ZeRO-1:    ✅ 完整      无需通信        AllReduce(2P)    AllGather 参数(P)    3P
                                                        ↑ 每卡只更新了 1/N，要拼回

ZeRO-2:    ✅ 完整      无需通信        ReduceScatter(P) AllGather 参数(P)    2P
                                       ↑ 砍掉了 AllGather 梯度

ZeRO-3:    ❌ 只有1/N   AllGather(P)×2  ReduceScatter(P) 不需要（反正只存 1/N） 3P
                        ↑ 前向取一次                     
                          反向再取一次
```

用 7B 模型 + 8 张 A100（80 GB/卡）作为 running example：

> P ≈ 参数量 × 每参数字节数（7B BF16 → P ≈ 14 GB）。ReduceScatter 和 AllGather 每次通信量各 ≈ P。

| 阶段 | 切分什么 | 每卡显存 | 通信操作 | 总量 | vs DDP |
|------|---------|---------|---------|-----|-------|
| **DDP** | 不切分 | 112 GB | ReduceScatter 梯度 + AllGather 梯度 | 2P | 1× |
| **ZeRO-1** | 优化器 | 38.5 GB | ReduceScatter 梯度 + AllGather 梯度 + AllGather 参数 | 3P | 1.5× |
| **ZeRO-2** | + 梯度 | 26.25 GB | ReduceScatter 梯度 + AllGather 参数 | 2P | 1× |
| **ZeRO-3** | + 参数 | 14 GB | ReduceScatter 梯度 + AllGather 参数(前向) + AllGather 参数(反向) | 3P | 1.5× |

ZeRO-2 和 DDP 通信量相同但显存更省，是性价比最高的阶段。

### 3.6 FSDP = PyTorch 原生的 ZeRO-3

FSDP（Fully Sharded Data Parallel）是 PyTorch 内置的 ZeRO-3 实现。功能几乎等价，区别在于：

| | ZeRO-3（DeepSpeed） | FSDP（PyTorch） |
|---|---|---|
| **实现** | 微软 DeepSpeed 库 | PyTorch 原生 (`torch.distributed.fsdp`) |
| **配置方式** | JSON 配置文件 | Python API |
| **灵活性** | 支持 CPU/NVMe Offload | 原生集成更好，但 Offload 支持较弱 |
| **社区** | 中小团队用得多 | Meta 系模型（LLaMA）用得多 |

LLaMA 3 训练使用了 FSDP 的 `SHARD_GRAD_OP` 模式（等价于 ZeRO-2），而不是 `FULL_SHARD`（ZeRO-3）。原因是 LLaMA 3 已经用了 TP 来切模型参数，FSDP 只需要切优化器和梯度就够了，没必要承受 ZeRO-3 的额外通信开销。

### 3.7 ZeRO 的限制

ZeRO 解决了显存问题——即使 70B 模型，ZeRO-3 + 8 卡也只需 70B × 16 / 8 = 140 GB / 8 = 17.5 GB/卡。但它有一个前提：**每张卡必须能放下至少一层的参数**（AllGather 恢复一层时，这一层的完整参数要临时放在显存里）。

对于超大模型（100B+），单层参数可能就超过单卡显存。这时候 ZeRO 也不够用了——必须把一层模型切到多张卡上。这就是模型并行（TP）要做的事。

## Part 4: 模型并行——把模型拆开

数据并行（DDP/ZeRO）的思路是"每卡看不同数据"。模型并行的思路完全不同——**把模型本身拆到多张卡上**。

两种拆法：
- **TP（Tensor Parallelism）**：把**一层**的矩阵切到多张卡——横着切或竖着切
- **PP（Pipeline Parallelism）**：把**不同层**放到不同卡——第 0-7 层在 GPU 0，第 8-15 层在 GPU 1

```
TP: 一层切成多份                PP: 不同层放不同卡

  GPU 0: [W 的左半]               GPU 0: [Layer 0-7]
  GPU 1: [W 的右半]               GPU 1: [Layer 8-15]
  每卡算一半，通信合并结果          数据流过 GPU 0 → GPU 1
```

### 4.1 TP：一层模型切到多张卡

TP 来自 Megatron-LM（Shoeybi et al., 2020），思路是把线性层的权重矩阵**切成多份**，分到不同卡上并行计算，再通过通信合并结果。

#### 两种切法：列切分和行切分

一个线性层 $Y = XW$，$X$ 是输入 $[B, S, d]$，$W$ 是权重 $[d, d']$。

**列切分（Column Parallel）**：把 $W$ 沿输出维度（列）切成 $N$ 份。

```
原始:  Y = X × W           W: [d, d']

列切分到 2 张卡:
  GPU 0:  Y_0 = X × W_0    W_0: [d, d'/2]  → Y_0: [B, S, d'/2]
  GPU 1:  Y_1 = X × W_1    W_1: [d, d'/2]  → Y_1: [B, S, d'/2]

  每卡拿到一半的输出。
  如果下一步需要完整的 Y → AllGather: [Y_0, Y_1] → Y: [B, S, d']
```

列切分的特点：每卡的输入 $X$ 是相同的（需要先 Broadcast 或每卡各自保有），每卡的输出是 $Y$ 的一部分。

**行切分（Row Parallel）**：把 $W$ 沿输入维度（行）切成 $N$ 份，同时把输入 $X$ 也切成 $N$ 份。

```
行切分到 2 张卡:
  GPU 0:  Y_0 = X_0 × W_0    X_0: [B, S, d/2], W_0: [d/2, d']  → Y_0: [B, S, d']
  GPU 1:  Y_1 = X_1 × W_1    X_1: [B, S, d/2], W_1: [d/2, d']  → Y_1: [B, S, d']

  每卡拿到的 Y_0、Y_1 是部分和（因为矩阵乘法按输入维度拆开后需要求和）
  AllReduce: Y = Y_0 + Y_1 → 完整结果
```

行切分的特点：每卡的输入是 $X$ 的一部分，每卡的输出需要 AllReduce 求和才能得到完整结果。

#### MLP 层的 TP 切法

Transformer 的 MLP（FFN）有两个线性层：up/gate（升维）和 down（降维）。Megatron-LM 的做法：

```
第一个线性层（gate_proj + up_proj）: 列切分
  每卡算一半的升维结果 → 不需要通信 → 直接送进激活函数

第二个线性层（down_proj）: 行切分
  接收上一步的部分结果作为输入 → 算完后 AllReduce 求和

整个 MLP 只需要 1 次 AllReduce → 通信开销最小
```

```
完整流程（2 卡 TP）:

  输入 x: [B, S, d]（两卡各持一份相同的 x）
    ↓
  gate_proj: 列切分   GPU 0 → [B, S, d_ff/2]
                      GPU 1 → [B, S, d_ff/2]
    ↓
  SwiGLU 激活（各卡独立算）
    ↓
  down_proj: 行切分   GPU 0 → [B, S, d]（部分和）
                      GPU 1 → [B, S, d]（部分和）
    ↓
  AllReduce: Y = Y_0 + Y_1  ← 唯一的一次通信
    ↓
  输出 Y: [B, S, d]（两卡都拿到完整结果）
```

#### Attention 层的 TP 切法

Attention 的多头结构天然适合 TP——**不同的头放到不同的卡上**。

```
8 个 Q 头，TP=2（两张卡）:
  GPU 0: Q头 0-3, K头 0-1（GQA 4 个 KV 头的前 2 个）, V头 0-1
  GPU 1: Q头 4-7, K头 2-3, V头 2-3

  各卡独立做自己那几个头的 QKV 投影 + Attention 计算（无通信）
  → 各卡拿到一半的头的输出 → concat → W_O 行切分 → AllReduce
```

和 MLP 一样，Attention 也只需要 **1 次 AllReduce**。所以一个 Transformer Block（Attention + MLP）总共 2 次 AllReduce。

#### 为什么 TP 必须在节点内

TP 每一层都要做 AllReduce，通信极其频繁。如果两张卡之间的带宽低，AllReduce 就会成为瓶颈。

```
节点内通信（NVLink）: ~600 GB/s   ← TP 放这里
节点间通信（InfiniBand）: ~50 GB/s  ← 慢 12 倍
```

一个 7B 模型的 MLP 层，AllReduce 的数据量约 2 × 7B/32层 × 2 字节 ≈ 0.88 GB/层。NVLink 下 ~1.5 ms，InfiniBand 下 ~18 ms。32 层的 Attention + MLP = 64 次 AllReduce，节点间要多花 ~1 秒/step——完全不可接受。

**所以 TP 只在节点内用（NVLink 连接的卡之间），节点间用 PP 或 DP。**

### 4.2 PP：不同层放不同卡

PP（Pipeline Parallelism）的思路最直观：模型有 32 层，4 张卡各放 8 层。数据从 GPU 0 流到 GPU 3。

```
GPU 0: Layer 0-7    →    GPU 1: Layer 8-15    →    GPU 2: Layer 16-23    →    GPU 3: Layer 24-31
  前向: 数据从左往右流
  反向: 梯度从右往左流
```

PP 的通信量很小——只在层与层的边界传递一次激活值（中间隐藏状态），不需要 AllReduce。

#### 气泡问题（Bubble）

PP 最大的问题是**气泡**——大部分卡在等待。

```
朴素 PP（1 个 micro-batch）的时间线:

  GPU 0: [前向] [等...] [等...] [等...] [等...] [等...] [反向] [等...]
  GPU 1:  [等.] [前向] [等...] [等...] [等...] [反向] [等...] [等...]
  GPU 2:  [等.] [等..] [前向] [等...] [反向] [等...] [等...] [等...]
  GPU 3:  [等.] [等..] [等..] [前向] [反向] [等...] [等...] [等...]

  大部分时间都在等 → 利用率极低
```

4 张卡但只有 1 张在工作 → 利用率约 25%。气泡比例 = $(P-1)/P$，$P$ = PP 并行度。

#### 解决方案：微批次填充

把一个大 batch 拆成多个 **micro-batch**，让流水线各阶段交替处理不同的 micro-batch：

```
GPipe（M=4 个 micro-batch）:

  GPU 0: [F1] [F2] [F3] [F4] [等] [B4] [B3] [B2] [B1]
  GPU 1:  [.] [F1] [F2] [F3] [F4] [B4] [B3] [B2] [B1]
  GPU 2:  [.] [..] [F1] [F2] [F3] [F4] [B4] [B3] [B2] [B1]
  GPU 3:  [.] [..] [..] [F1] [F2] [F3] [F4] [B4] [B3] [B2] [B1]

  F = 前向, B = 反向, 数字 = micro-batch 编号
  气泡从 75% 降到约 (P-1)/(M+P-1) = 3/7 ≈ 43%
```

micro-batch 越多，气泡越小。但 micro-batch 越多，每个 micro-batch 越小，计算效率也会下降。

更高级的调度策略（1F1B、Interleaved 1F1B、Zero-Bubble PP、DualPipe）可以把气泡进一步压缩，详见附录 A.1。

### 4.3 TP vs PP 怎么选

| | TP | PP |
|---|---|---|
| **切什么** | 一层的权重矩阵 | 不同层 |
| **通信频率** | 每层 2 次 AllReduce | 只在层边界传激活值 |
| **通信量** | 大（权重大小级别） | 小（隐藏状态大小） |
| **对带宽要求** | 极高 → 必须节点内 NVLink | 较低 → 可以跨节点 IB |
| **利用率** | 接近 100%（无气泡） | 有气泡（micro-batch 越多越好） |
| **适用场景** | 单机多卡（8 卡 NVLink） | 多机多卡（节点间） |

**经验法则**：
- **节点内**用 TP（NVLink 带宽够）
- **节点间**用 PP（IB 带宽不够跑 TP）
- 两者经常组合使用（见 Part 5）

## Part 5: 组合策略 + 面试真题

### 5.1 3D 并行 = DP + TP + PP

实际训练大模型，三种并行策略同时使用：

```
64 张卡 = 8 个节点 × 每节点 8 张卡

节点内 8 卡: TP=4（4 卡做张量并行）× DP=2（2 组数据并行）
节点间 8 节点: PP=8（8 个流水线阶段）

或者另一种常见配置:
节点内 8 卡: TP=8（整个节点做张量并行）
节点间: PP=4 × DP=2
```

选择原则：
1. **TP 放节点内**——通信量大，需要 NVLink
2. **PP 放节点间**——通信量小，IB 够用
3. **DP 填充剩余卡**——加速训练

### 5.2 【字节真题】8 卡 A100 训 7B 模型，怎么配并行策略？

**答案**：纯 DDP 或 ZeRO-2，不需要 TP/PP。

推理过程：

```
7B 模型状态 = 112 GB
每卡显存 = 80 GB

方案 1: 纯 DDP
  每卡 112 GB → 放不下 80 GB 的卡 ✗

方案 2: ZeRO-1（切优化器状态）
  每卡 = 14(参数) + 14(梯度) + 84/8(优化器) = 38.5 GB → 放得下 ✓
  剩余 80 - 38.5 = 41.5 GB 给激活值 → 足够

方案 3: ZeRO-2（切优化器 + 梯度）
  每卡 = 14 + 14/8 + 84/8 = 26.25 GB → 更宽裕
  适合开更大的 batch size 或更长的 seq_len

不需要 TP/PP:
  7B 模型单层参数约 7B/32 × 2 = 0.44 GB，一张卡完全放得下
  8 卡在同一节点内，DDP/ZeRO 的通信走 NVLink，够快
  加 TP/PP 反而增加复杂度和通信开销，得不偿失
```

**面试延伸**：如果面试官追问"训 70B 呢？"

```
70B 模型状态 = 1120 GB
8 卡 × 80 GB = 640 GB

即使 ZeRO-3: 1120 / 8 = 140 GB → 还是放不下单卡 80 GB ✗
需要 TP: 节点内 TP=8，把每层切到 8 卡上
  再配合 ZeRO-2 切优化器和梯度
如果多节点: TP=8(节点内) + PP=N(节点间) + DP(剩余卡)
```

### 5.3 业界实例

#### LLaMA 3 405B（基于 Meta 技术报告）

```
总卡数: 16384 张 H100
并行配置: TP=8 × PP=16 × DP=128
  - TP=8: 每个节点 8 卡做张量并行（NVLink）
  - PP=16: 16 个流水线阶段（跨节点，IB）
  - DP=128: 128 路数据并行
  - 每路 DP 用 FSDP SHARD_GRAD_OP（≈ ZeRO-2）
训练数据: 15T tokens
MFU: 约 38%-43%
```

#### DeepSeek V3 671B（基于其技术报告）

```
总卡数: 2048 张 H800
并行配置: EP=64 × DP=32（无 PP）

  - DP=32: 32 路数据并行 + ZeRO-1
  - TP=1: 没用张量并行（靠 MoE 的稀疏激活省显存）
```

DeepSeek V3 的关键：MoE 架构只激活 37B/671B 参数 → 计算量接近 37B dense 模型 → 不需要 TP 也能跑 → 省了 TP 的通信开销 → 成本极低。

## 附录 A: 深水区选读

> 以下内容面试低频或深水区专用。了解概念即可，不需要背公式。

### A.1 PP 高级调度策略

| 策略 | 核心思想 | 气泡率 |
|------|---------|--------|
| **GPipe** | 先做完所有 micro-batch 的前向，再做反向 | $(P-1)/(M+P-1)$ |
| **1F1B** | 前向和反向交替执行，尽早释放激活值显存 | 同 GPipe，但峰值显存更低 |
| **Interleaved 1F1B** | 每张卡放多个不连续的层（虚拟流水线），增加并行度 | 气泡减半 |
| **Zero-Bubble PP** | 通信和计算完全重叠，允许异步调度 | 接近 0 |
| **DualPipe（DeepSeek V3）** | 双向流水线，正向和反向同时进行 | 接近 0 |

### A.2 SP / CP / EP 简介

| 并行方式 | 切什么 | 解决什么问题 |
|---------|--------|-------------|
| **SP（Sequence Parallelism）** | 序列维度上的非 TP 算子（LayerNorm、Dropout） | TP 只切了矩阵乘，其他算子的激活值仍然每卡一份，SP 切掉这部分冗余 |
| **CP（Context Parallelism）** | 整个序列切成多段，各卡处理一段 | 超长上下文（128K+）时，单卡放不下完整序列的激活值 |
| **EP（Expert Parallelism）** | MoE 的不同专家放不同卡 | 专家太多放不下；用 All-to-All 通信把 token 路由到对应专家 |

### A.3 混合精度与 FP8

**混合精度**的核心：前向/反向用 BF16 省显存和加速计算，master weights 和优化器用 FP32 保精度。详细机制已在 [11-预训练](11-预训练.md) 的"混合精度训练的显存节省机制"小节中讲解。

#### FP8 训练：只加速矩阵乘法，其他一切不变

**最关键的一句话**：FP8 训练不是"把整个模型换成 8 bit"。它**只在矩阵乘法（GEMM）这一步**把输入从 BF16 临时转成 FP8、算完立刻转回 BF16，其他所有操作（LayerNorm、Softmax、Attention、优化器）照旧用 BF16/FP32。

为什么只动矩阵乘法？因为 Transformer 的计算时间绑定在两个地方：Attention 的 $QK^T$ 和 FFN 的三个线性层。这些全是矩阵乘法，占了总算力的绝大部分。H100 的 Tensor Core 做 FP8 矩阵乘的吞吐是 BF16 的 2 倍——只要把矩阵乘换成 FP8，整体训练就能快约 30%。

完整流程（以一个线性层 $Y = XW$ 为例）：

```
BF16 混合精度训练（11 章讲的）:
  X (BF16) × W (BF16) → Y (BF16) → 后续操作

FP8 训练（在上面基础上改一步）:
  X (BF16) → 量化 → X' (FP8)  ┐
                                ├→ X' × W' (FP8 GEMM, Tensor Core) → Y (BF16)
  W (BF16) → 量化 → W' (FP8)  ┘                                     ↓
                                                              后续操作照旧（BF16）
```

**量化 = 除以一个 scaling factor 再四舍五入到 FP8。反量化 = 乘回 scaling factor。** 结果在数学上近似等价，但 Tensor Core 算得快一倍。

#### FP8 的两种格式

| 格式 | 指数位 | 尾数位 | 最大值 | 精度 | 用在哪 |
|------|-------|-------|-------|------|--------|
| **E4M3** | 4 | 3 | 448 | 较高 | 前向传播（需要精度） |
| **E5M2** | 5 | 2 | 57344 | 较低 | 反向传播（梯度范围大） |

DeepSeek V3 统一用 E4M3，配合细粒度量化来弥补动态范围不足。

#### 为什么需要细粒度量化（per-block scaling）

FP8 只有 8 bit，能表示的数值范围很窄。如果一个矩阵里既有很大的值（如 100）又有很小的值（如 0.001），一个 scaling factor 照顾不了两头：

```
问题: 整个张量用同一个 scaling factor（per-tensor scaling）

  张量: [0.001, 0.002, 100.0, 0.003]
  scaling factor 要照顾 100.0 → 设为大值 → 0.001 和 0.002 四舍五入变成 0 → 精度丢失

解法: 分成小块，每块用自己的 scaling factor（per-block scaling）

  块 1: [0.001, 0.002] → scaling factor 小 → 0.001 和 0.002 都能精确表示
  块 2: [100.0, 0.003] → scaling factor 大 → 各自精度都够用
```

DeepSeek V3 的分块方式：
- **激活值**：按 1×128 分块（每个 token 的每 128 个通道一块）
- **权重**：按 128×128 分块

#### FP32 累加：块间求和用高精度

矩阵乘法 $C = A \times B$ 的计算过程是"逐元素乘再累加"。FP8 乘法的结果用 FP8 累加的话，累加几千次后误差会放大到不可接受。

```
朴素累加（FP8 精度）:
  c = a_0*b_0 + a_1*b_1 + ... + a_4095*b_4095
  累加 4096 次，每次四舍五入，误差逐步积累 → 最终误差可达 2%

分块累加（DeepSeek V3 的做法）:
  把 4096 维分成 32 个 128 维的块
  块内: FP8 累加（128 次，误差可控）
  块间: 提升到 FP32 累加（32 次，高精度合并）→ 误差忽略不计
```

#### 哪些操作用 FP8，哪些不用

| 操作 | 精度 | 原因 |
|------|------|------|
| 线性层（MLP、QKV 投影、W_O） | **FP8** | 矩阵乘法，Tensor Core 加速 |
| LayerNorm / RMSNorm | BF16/FP32 | 涉及均值/方差统计，对精度敏感 |
| Softmax | FP32 | 指数运算，数值不稳定 |
| Attention（$QK^T$、$\text{attn} \times V$） | BF16 | Flash Attention 走专门的 kernel |
| Embedding / LM Head | BF16 | 对精度敏感 |
| 优化器（AdamW） | FP32 | master weights 必须高精度 |
| MoE Gating | BF16 | 路由决策对精度敏感 |

**一句话总结**：FP8 训练 = BF16 混合精度训练 + 把线性层的矩阵乘法临时降到 FP8。其他全部不变。H100 上约快 30%，精度几乎无损。

### A.4 DeepSpeed vs Megatron-LM

| | DeepSpeed（微软） | Megatron-LM（NVIDIA） |
|---|---|---|
| **核心贡献** | ZeRO 系列优化器 | Tensor Parallelism + Pipeline Parallelism |
