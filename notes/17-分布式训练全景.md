## 一、集合通信原语

### 为什么需要理解通信原语？

分布式训练的本质是"多个 GPU 各算各的，然后通过通信协调结果"。所有并行策略（DP/TP/PP/CP/EP）最终都要落到几个基本的通信操作上。理解这些原语，后面的并行策略就是"在哪一步插入哪个通信操作"的问题。

### 六种基本操作

#### 1. Broadcast（广播）

一个 GPU 的数据复制到所有 GPU。

```
操作前:                    操作后:
GPU 0: [A]                GPU 0: [A]
GPU 1: [ ]       →        GPU 1: [A]
GPU 2: [ ]                GPU 2: [A]
GPU 3: [ ]                GPU 3: [A]
```

用途：模型初始化时，rank 0 加载权重后广播给所有卡。

#### 2. Reduce（归约）

所有 GPU 的数据做归约运算（如求和），结果只存在目标 GPU。

```
操作前:                    操作后（sum, dst=0）:
GPU 0: [A₀]              GPU 0: [A₀+A₁+A₂+A₃]
GPU 1: [A₁]      →       GPU 1: [ ]
GPU 2: [A₂]              GPU 2: [ ]
GPU 3: [A₃]              GPU 3: [ ]
```

#### 3. AllReduce（全归约）

所有 GPU 的数据做归约运算，结果存在每一个 GPU 上。等价于 Reduce + Broadcast。

```
操作前:                    操作后（sum）:
GPU 0: [A₀]              GPU 0: [A₀+A₁+A₂+A₃]
GPU 1: [A₁]      →       GPU 1: [A₀+A₁+A₂+A₃]
GPU 2: [A₂]              GPU 2: [A₀+A₁+A₂+A₃]
GPU 3: [A₃]              GPU 3: [A₀+A₁+A₂+A₃]
```

用途：**DDP 的核心操作**——每张卡计算各自的梯度后，AllReduce 求平均，使所有卡拿到相同的梯度。

#### 4. AllGather（全收集）

每个 GPU 贡献一个分片，操作后每个 GPU 持有完整数据（所有分片的拼接）。

```
操作前:                    操作后:
GPU 0: [A₀]              GPU 0: [A₀, A₁, A₂, A₃]
GPU 1: [A₁]      →       GPU 1: [A₀, A₁, A₂, A₃]
GPU 2: [A₂]              GPU 2: [A₀, A₁, A₂, A₃]
GPU 3: [A₃]              GPU 3: [A₀, A₁, A₂, A₃]
```

用途：**ZeRO-3/FSDP 的核心操作**——参数被切分存储，前向/反向计算前 AllGather 收集完整参数。

#### 5. ReduceScatter（归约分散）

先对所有 GPU 的数据做归约，然后把结果分片分散到各 GPU。

```
操作前（每个 GPU 有 4 个块）:
GPU 0: [a₀, b₀, c₀, d₀]
GPU 1: [a₁, b₁, c₁, d₁]
GPU 2: [a₂, b₂, c₂, d₂]
GPU 3: [a₃, b₃, c₃, d₃]

操作后（sum + scatter）:
GPU 0: [Σaᵢ]
GPU 1: [Σbᵢ]
GPU 2: [Σcᵢ]
GPU 3: [Σdᵢ]
```

用途：**ZeRO-2 的梯度归约**——梯度求和后直接分片存储，不像 AllReduce 那样每卡都存完整梯度。

**关键关系：AllReduce = ReduceScatter + AllGather**。先把数据分片归约到各卡，再收集拼接。这个分解是 Ring AllReduce 算法的基础。

#### 6. AlltoAll（全交换）

每个 GPU 向每个其他 GPU 发送一个不同的数据块。

```
操作前:                           操作后:
GPU 0: [a₀₀, a₀₁, a₀₂, a₀₃]   GPU 0: [a₀₀, a₁₀, a₂₀, a₃₀]
GPU 1: [a₁₀, a₁₁, a₁₂, a₁₃]   GPU 1: [a₀₁, a₁₁, a₂₁, a₃₁]
GPU 2: [a₂₀, a₂₁, a₂₂, a₂₃]   GPU 2: [a₀₂, a₁₂, a₂₂, a₃₂]
GPU 3: [a₃₀, a₃₁, a₃₂, a₃₃]   GPU 3: [a₀₃, a₁₃, a₂₃, a₃₃]
```

可以理解为矩阵转置：第 $i$ 行第 $j$ 列的数据，从 GPU $i$ 发送到 GPU $j$。

用途：**Expert Parallelism 的核心操作**——MoE 中 token 被路由到不同专家所在的 GPU，需要 AlltoAll 重新分配 token。

### Ring AllReduce 算法

朴素的 AllReduce（每卡把梯度发给所有其他卡）通信量是 $O(N \cdot M)$，$N$ 是 GPU 数，$M$ 是数据量。Ring AllReduce 把通信量降到 $O(M)$，与 GPU 数无关。

#### 核心思想

把 $N$ 个 GPU 排成环形。把数据分成 $N$ 个块。分两个阶段执行：

**阶段一：ReduceScatter（N-1 步）**

每步中，每个 GPU 把自己的一个块发给下一个 GPU，同时从上一个 GPU 接收一个块并累加。$N-1$ 步后，每个 GPU 持有一个块的完整归约结果。

```
4 个 GPU，数据分 4 块，ReduceScatter 阶段：

初始:
GPU 0: [a₀, b₀, c₀, d₀]
GPU 1: [a₁, b₁, c₁, d₁]
GPU 2: [a₂, b₂, c₂, d₂]
GPU 3: [a₃, b₃, c₃, d₃]

Step 1: GPU i 把第 i 块发给 GPU (i+1)%4
GPU 0: [a₀,    b₀,        c₀,    d₀+d₃]     ← 收到 GPU3 的 d₃
GPU 1: [a₁+a₀, b₁,        c₁,    d₁]         ← 收到 GPU0 的 a₀
GPU 2: [a₂,    b₂+b₁,     c₂,    d₂]         ← 收到 GPU1 的 b₁
GPU 3: [a₃,    b₃,         c₃+c₂, d₃]        ← 收到 GPU2 的 c₂

Step 2: 继续传递已经部分归约的块
GPU 0: [a₀,    b₀,         c₀+c₃+c₂, d₀+d₃]
GPU 1: [a₁+a₀, b₁,         c₁,        d₁+d₀+d₃]
GPU 2: [a₂+a₁+a₀, b₂+b₁,  c₂,        d₂]
GPU 3: [a₃,    b₃+b₂+b₁,   c₃+c₂,    d₃]

Step 3: 最后一步
GPU 0: [a₀+Σ完成, b₀,         c₀+Σ完成, d₀+d₃]    ← GPU0 的块 a 完成归约
...（每个 GPU 恰好有一个块完成了全部归约）
```

**阶段二：AllGather（N-1 步）**

类似过程，但不累加，只是转发完整归约后的块。$N-1$ 步后，每个 GPU 持有所有块的归约结果。

#### 通信量分析

每个阶段 $N-1$ 步，每步传输 $M/N$ 的数据。总通信量：

$$\text{每个 GPU 的发送量} = 2 \times (N-1) \times \frac{M}{N} = 2M \cdot \frac{N-1}{N}$$

当 $N$ 很大时，趋近于 $2M$——和 GPU 数量无关。这就是 Ring AllReduce 的核心优势：**带宽最优（bandwidth-optimal）**，增加 GPU 不增加每卡通信量。

### NCCL vs Gloo

| 特性 | NCCL | Gloo |
|------|------|------|
| 全称 | NVIDIA Collective Communications Library | Facebook 开源通信库 |
| 硬件 | 仅 NVIDIA GPU | CPU + GPU（包括非 NVIDIA） |
| 性能 | 极致优化（利用 NVLink、NVSwitch、IB） | 通用但较慢 |
| 用途 | **GPU 训练的默认选择** | CPU 训练、调试 |
| PyTorch 初始化 | `dist.init_process_group(backend="nccl")` | `dist.init_process_group(backend="gloo")` |

MiniMind 在 `trainer/trainer_utils.py:48` 中使用 `backend="nccl"`。

## 二、数据并行（Data Parallelism）

### 为什么需要数据并行？

单卡训练速度受限于计算能力和 batch size。数据并行的目标很直接：**让 N 张卡同时处理 N 倍的数据，训练速度接近线性加速**。前提是模型能放得下一张卡。

### DDP（DistributedDataParallel）— MiniMind 用的

#### 基本原理

```
GPU 0: 完整模型副本 + 数据分片 A → 梯度 A ─┐
GPU 1: 完整模型副本 + 数据分片 B → 梯度 B ─┤ AllReduce（求平均）
GPU 2: 完整模型副本 + 数据分片 C → 梯度 C ─┤
GPU 3: 完整模型副本 + 数据分片 D → 梯度 D ─┘
                                              ↓
所有 GPU 得到相同的平均梯度 → 各自用相同的优化器更新 → 权重保持同步
```

#### 关键机制 1：DistributedSampler

每张卡必须处理不同的数据分片。`DistributedSampler` 负责把 dataset 按 rank 均匀切分：

```python
# trainer/train_pretrain.py:136
train_sampler = DistributedSampler(train_ds) if dist.is_initialized() else None
```

`DistributedSampler` 的核心逻辑：把全部样本索引 `[0, 1, 2, ..., N-1]` 按 world_size 交错分配（或按块分配），每个 rank 只看到 $1/N$ 的数据。

每个 epoch 开始时需要调用 `set_epoch(epoch)` 来改变 shuffle 的种子，否则每个 epoch 各卡拿到的数据分配一样：

```python
# trainer/train_pretrain.py:158
train_sampler and train_sampler.set_epoch(epoch)
```

#### 关键机制 2：Gradient Bucket 和通信-计算重叠

DDP 的精妙之处不只是在 backward 结束后做一次 AllReduce。它通过 **gradient bucket** 机制实现了通信与计算的重叠：

```
反向传播过程（从最后一层开始）:

Layer 8 梯度计算完毕 → 装入 Bucket 3
Layer 7 梯度计算完毕 → 装入 Bucket 3
                        ↓ Bucket 3 满了
              ┌─ AllReduce Bucket 3（通信，异步执行）
              │
Layer 6 梯度计算完毕 → 装入 Bucket 2   ← 同时在计算！
Layer 5 梯度计算完毕 → 装入 Bucket 2
                        ↓ Bucket 2 满了
              ┌─ AllReduce Bucket 2（通信）
              │
Layer 4 梯度计算完毕 → ...
...
```

**原理**：PyTorch DDP 把模型参数按逆序（反向传播的顺序）分成多个 bucket（默认 25MB 一个）。每当一个 bucket 中所有参数的梯度都计算完毕，立刻启动该 bucket 的 AllReduce，同时 GPU 继续计算其他层的梯度。

这样，通信和计算是**重叠执行**的，等到最前面几层的梯度算完，大部分 AllReduce 也已经完成了。理想情况下，通信开销被完全隐藏。

#### MiniMind 中的 DDP 代码

```python
# trainer/trainer_utils.py:44-51
def init_distributed_mode():
    if int(os.environ.get("RANK", -1)) == -1:
        return 0  # 非 DDP 模式，单卡直接返回
    dist.init_process_group(backend="nccl")  # 初始化 NCCL 通信后端
    local_rank = int(os.environ["LOCAL_RANK"])
    torch.cuda.set_device(local_rank)        # 绑定当前进程到对应 GPU
    return local_rank

# trainer/train_pretrain.py:110, 154

```

启动方式：`torchrun --nproc_per_node=2 trainer/train_pretrain.py`

`torchrun` 会自动设置环境变量 `RANK`、`LOCAL_RANK`、`WORLD_SIZE`，并为每张卡启动一个进程。

#### DDP 的显存占用

$$\text{每卡显存} = \underbrace{P}_{\text{参数}} + \underbrace{P}_{\text{梯度}} + \underbrace{O}_{\text{优化器状态}} + \underbrace{A}_{\text{激活值}}$$

其中优化器状态 $O$ 包括 Adam 的一阶动量 $m$ 和二阶动量 $v$，各占参数量的大小。所以 Adam 下 $O = 2P$（FP32 下额外 $2 \times 4B \times P = 8B \times P$）。

**问题：4 张卡各存一份完整的参数、梯度、优化器状态，3/4 是冗余。** ZeRO 解决的就是这个问题。

## 三、ZeRO（Zero Redundancy Optimizer）

### 为什么需要 ZeRO？

DDP 每张卡存储完整的模型参数、梯度、优化器状态。以 1B 参数 + Adam + 混合精度训练为例：

| 组件 | 每卡存储量 |
|------|-----------|
| FP16 参数 | $1B \times 2B = 2\text{GB}$ |
| FP16 梯度 | $1B \times 2B = 2\text{GB}$ |
| FP32 master weights | $1B \times 4B = 4\text{GB}$ |
| FP32 Adam m（一阶动量） | $1B \times 4B = 4\text{GB}$ |
| FP32 Adam v（二阶动量） | $1B \times 4B = 4\text{GB}$ |
| **合计** | **16 GB**（不含激活值） |

用 $\Psi$ 表示参数量。混合精度 Adam 下，DDP 每卡存储：

$$\text{每卡} = 2\Psi + 2\Psi + (4\Psi + 4\Psi + 4\Psi) = 4\Psi + 12\Psi = 16\Psi \text{ bytes}$$

其中 $4\Psi$（FP16 参数 + FP16 梯度）和 $12\Psi$（FP32 master weights + Adam m + Adam v）。4 张卡就是 $4 \times 16\Psi$ 的总存储，但实际上只需要 $16\Psi$。

ZeRO 的核心思想：**这些冗余数据不需要每卡都存完整副本，切分到各卡上，需要时再收集。**

### ZeRO 三个阶段

#### ZeRO-1：切分优化器状态

只把 optimizer states（Adam 的 $m$、$v$、FP32 master weights）切分到 $N$ 张卡。

```
4 卡 ZeRO-1:
GPU 0: 完整 FP16 参数 + 完整 FP16 梯度 + 1/4 optimizer states (m₀, v₀, w₀)
GPU 1: 完整 FP16 参数 + 完整 FP16 梯度 + 1/4 optimizer states (m₁, v₁, w₁)
GPU 2: 完整 FP16 参数 + 完整 FP16 梯度 + 1/4 optimizer states (m₂, v₂, w₂)
GPU 3: 完整 FP16 参数 + 完整 FP16 梯度 + 1/4 optimizer states (m₃, v₃, w₃)
```

每卡存储从 $16\Psi$ 降到 $4\Psi + 12\Psi/N$。4 卡时 = $4\Psi + 3\Psi = 7\Psi$，相比 DDP 的 $16\Psi$ 省了约 **2.3 倍**。

**通信量**：和 DDP 一样，$2\Psi$。反向传播后梯度做 **ReduceScatter**（$\Psi$，每张卡只保留自己 optimizer 分片对应的归约梯度），各卡用自己负责的那部分 optimizer states 更新对应分片的参数，最后 **AllGather** 更新后的参数（$\Psi$）同步到所有卡。总通信量 = ReduceScatter 梯度 $\Psi$ + AllGather 参数 $\Psi$ = $2\Psi$。

等等——DDP 不需要 AllGather 参数（因为每卡都存了完整参数），ZeRO-1 为什么也不需要多付通信？因为 DDP 的 AllReduce 本身就是 $2\Psi$（ReduceScatter $\Psi$ + AllGather $\Psi$ 的组合），ZeRO-1 只是把同样的通信预算重新分配：梯度的 AllGather 那 $\Psi$ 省下来（梯度不再每卡同步全量，只留分片），挪给参数的 AllGather。一进一出正好抵消——这是 ZeRO 论文的核心卖点之一：P_os 和 P_os+g 通信量与 DDP 相同，只有 ZeRO-3 增至 $3\Psi$（见下文）。

#### ZeRO-2：切分梯度 + 优化器状态

梯度也不需要每卡存完整。反向传播时用 **ReduceScatter** 代替 AllReduce：

```
4 卡 ZeRO-2:
GPU 0: 完整 FP16 参数 + 1/4 FP16 梯度 + 1/4 optimizer states
GPU 1: 完整 FP16 参数 + 1/4 FP16 梯度 + 1/4 optimizer states
GPU 2: 完整 FP16 参数 + 1/4 FP16 梯度 + 1/4 optimizer states
GPU 3: 完整 FP16 参数 + 1/4 FP16 梯度 + 1/4 optimizer states
```

每卡存储 = $2\Psi + (2\Psi + 12\Psi)/N$。4 卡时 = $2\Psi + 3.5\Psi = 5.5\Psi$，比 ZeRO-1 又省了。

**通信量**：ReduceScatter 梯度 $\Psi$ + AllGather 参数 $\Psi$ = $2\Psi$。和 DDP 的 AllReduce ($2\Psi$) 一样，没有额外通信开销。

#### ZeRO-3：参数也切分

参数、梯度、优化器状态全部均匀切分到 $N$ 张卡。

```
4 卡 ZeRO-3:
GPU 0: 1/4 FP16 参数 + 1/4 FP16 梯度 + 1/4 optimizer states
GPU 1: 1/4 FP16 参数 + 1/4 FP16 梯度 + 1/4 optimizer states
GPU 2: 1/4 FP16 参数 + 1/4 FP16 梯度 + 1/4 optimizer states
GPU 3: 1/4 FP16 参数 + 1/4 FP16 梯度 + 1/4 optimizer states
```

每卡存储 = $16\Psi / N$。4 卡时 = $4\Psi$，**线性节省**。

**代价**：前向和反向传播时，每一层计算都需要 AllGather 收集完整参数，计算完毕后释放。通信量 = 前向 AllGather $\Psi$ + 反向 AllGather $\Psi$ + 反向 ReduceScatter $\Psi$ = $3\Psi$，比 DDP 多了 $\Psi$。

```
ZeRO-3 的一次前向 + 反向：

Layer i 前向:
  AllGather 第 i 层参数（从所有卡收集）
  → 执行前向计算
  → 释放第 i 层参数（显存释放）

Layer i 反向:
  AllGather 第 i 层参数（再次收集）
  → 计算梯度
  → ReduceScatter 梯度（归约后分片存储）
  → 释放第 i 层参数
```

#### ZeRO 各阶段对比

| | DDP | ZeRO-1 | ZeRO-2 | ZeRO-3 |
|---|---|---|---|---|
| 切分内容 | 无 | Optimizer States | + Gradients | + Parameters |
| 每卡显存（混合精度 Adam） | $16\Psi$ | $4\Psi + 12\Psi/N$ | $2\Psi + 14\Psi/N$ | $16\Psi/N$ |
| 4 卡时每卡 | $16\Psi$ | $7\Psi$ | $5.5\Psi$ | $4\Psi$ |
| 通信量 | $2\Psi$ | $2\Psi$ | $2\Psi$ | $3\Psi$ |
| 通信操作 | AllReduce | ReduceScatter + AllGather | ReduceScatter + AllGather | 3× AllGather/ReduceScatter |

### ZeRO-Infinity：CPU 和 NVMe 卸载

当 GPU 显存不够时，ZeRO-Infinity 把 optimizer states、梯度甚至参数卸载到 CPU 内存或 NVMe SSD：

```
层级:           GPU HBM (80GB)  →  CPU RAM (512GB+)  →  NVMe SSD (TB级)
速度:           ~2 TB/s            ~50 GB/s              ~5 GB/s
适合存储:       激活值 + 当前层参数    optimizer states     不常用的参数分片
```

**工作流程**：计算时从 CPU/NVMe 预取（prefetch）需要的参数到 GPU，计算完毕后卸载回去。

**代价**：吞吐量显著下降（CPU 内存带宽约 50 GB/s vs GPU HBM 约 2 TB/s），但能训更大的模型。适合"GPU 实在放不下"的场景，不适合追求训练速度的场景。

### ZeRO-R：激活值优化

ZeRO-R 不是 ZeRO-1/2/3 的延续，而是正交的优化方向。它把**激活值**（前向传播的中间结果，反向传播时需要）做分区：

- 激活值切分到多卡，需要时 AllGather
- 配合 activation checkpointing（Ch09 训练基础）使用效果更好
- 还优化了临时 buffer 和内存碎片

## 四、FSDP（Fully Sharded Data Parallel）

### 为什么需要 FSDP？

ZeRO 是 DeepSpeed 框架的核心功能，但 DeepSpeed 是微软的独立框架，不是 PyTorch 原生的。PyTorch 团队开发了 FSDP 作为 **ZeRO-3 的 PyTorch 原生实现**，让用户不需要额外安装框架就能享受参数分片的显存节省。

### FSDP 和 ZeRO 的对应关系

| FSDP 策略 | ZeRO 等价 | 效果 |
|-----------|----------|------|
| `FULL_SHARD` | ZeRO-3 | 参数 + 梯度 + 优化器状态全部分片 |
| `SHARD_GRAD_OP` | ZeRO-2 | 梯度 + 优化器状态分片，参数不分片 |
| `NO_SHARD` | DDP | 不分片，等同于普通 DDP |

### FSDP 的工作流程（FULL_SHARD 模式）

```
前向传播:
  对每个 FSDP unit（通常是一个 Transformer Block）:
    1. AllGather 该 unit 的完整参数
    2. 执行前向计算
    3. 丢弃非本卡负责的参数分片（释放显存）

反向传播:
  对每个 FSDP unit（从后往前）:
    1. AllGather 该 unit 的完整参数
    2. 计算梯度
    3. ReduceScatter 梯度（归约 + 分片存储）
    4. 丢弃非本卡负责的参数分片
```

### LLaMA 3 用 FSDP SHARD_GRAD_OP（ZeRO-2）的原因

LLaMA 3 405B 的训练论文明确提到使用 FSDP，但选择的是 `SHARD_GRAD_OP`（等价于 ZeRO-2）而不是 `FULL_SHARD`（ZeRO-3）。原因：

1. **避免额外的前向 AllGather**：ZeRO-3 在前向传播时每层都要 AllGather 参数，计算完再释放，反向传播时再 AllGather 一次。ZeRO-2 保留完整参数，省掉了前向的 AllGather。
2. **减少通信量**：ZeRO-2 通信量 $2\Psi$，和 DDP 相同；ZeRO-3 通信量 $3\Psi$。
3. **显存够用**：LLaMA 3 使用了 16,384 张 H100（各 80GB HBM），Tensor Parallel 和 Pipeline Parallel 已经大幅切分了模型，每个 DP rank 上的模型分片足够小，ZeRO-2 就够了。

论文原文（基于 Meta 公开的技术报告）："We do not reshard after forward computation to avoid an extra all-gather communication during backward passes."

### FSDP vs DeepSpeed 选型建议

| 维度 | FSDP | DeepSpeed |
|------|------|-----------|
| 集成度 | PyTorch 原生，无额外依赖 | 需要安装 `deepspeed` 包 |
| Hugging Face | `Trainer` 直接支持 | 需要 JSON 配置文件 |
| MoE 支持 | 基础支持 | 更成熟（专家分片、EP） |
| CPU/NVMe offload | FSDP 支持 CPU offload | ZeRO-Infinity 支持 CPU + NVMe |
| 性能（<7B） | 通常更快（轻量级开销） | 稍慢（框架开销） |
| 性能（7B+） | 接近 | 接近 |
| 社区趋势 | PyTorch 2.x 默认推荐 | MoE、极大模型场景仍主流 |

**一般建议**：fine-tuning 7B-70B dense 模型，FSDP 是更简单的选择；训练超大 MoE 模型或需要 NVMe offload，DeepSpeed ZeRO-Infinity 更成熟。

## 四点五、DeepSpeed vs Megatron-LM：两大框架全景

前面几节讲了 DDP、ZeRO、FSDP、TP、PP 这些具体的并行技术。但实际训练时，你不会自己从头实现这些——你用的是**训练框架**，框架把这些技术打包好。业界两大框架就是 **DeepSpeed**（微软）和 **Megatron-LM**（NVIDIA），它们各自主攻不同的问题维度，而且可以组合使用。这一节讲清楚它们的全貌、核心差异和组合方式。

### 它们各自解决什么问题？

一句话概括：**DeepSpeed 解决"存不下"，Megatron 解决"算不动"。**

```
普通 DDP 的瓶颈：

  每张 GPU 存了一份完整的模型状态（参数 + 梯度 + 优化器状态）
  ↓
  显存爆了（7B 模型需要 112GB，一张 80G 的 A100 放不下）
  ↓
  两条路：
  
  路线 A：还是每卡算完整的层，但把"存储"分摊    → DeepSpeed ZeRO
  路线 B：把"计算"也切开，每卡只算一层的一部分   → Megatron TP
```

### DeepSpeed（微软）

#### 核心贡献：ZeRO

ZeRO 的详细技术原理已经在第三节讲过。这里从框架视角补充 DeepSpeed 的**全貌**——它不只有 ZeRO。

DeepSpeed 是一个**训练优化库**，围绕"降低显存、降低门槛"展开，核心模块包括：

| 模块 | 解决什么 | 对应技术 |
|------|---------|---------|
| **ZeRO-1/2/3** | 模型状态的显存冗余 | 切分 optimizer states / gradients / parameters |
| **ZeRO-Infinity** | GPU 显存完全不够 | 参数和优化器状态卸载到 CPU RAM / NVMe SSD |
| **ZeRO-R** | 激活值显存占用 | 激活值分区 + checkpointing |
| **混合精度训练** | 训练速度和显存 | FP16/BF16 自动混合精度 |
| **Pipeline Parallelism** | 模型太大放不下单节点 | 按层切分（类似 GPipe 的调度） |
| **MoE 支持** | 专家模型训练 | Expert Parallelism、专家负载均衡 |
| **Sparse Attention** | 长序列注意力计算 | 稀疏注意力模式 |
| **Inference 优化** | 推理加速 | DeepSpeed-Inference（量化、kernel fusion） |

#### 为什么说 DeepSpeed "易用"？

DeepSpeed 的设计哲学是**最小侵入**——不需要改模型代码，只需要：

```python
# 原始 PyTorch 训练代码
model = MyModel()
optimizer = AdamW(model.parameters(), lr=1e-4)

# 改成 DeepSpeed：加两行，传一个 JSON 配置
import deepspeed
model, optimizer, _, _ = deepspeed.initialize(
    model=model,
    optimizer=optimizer,
    config="ds_config.json"  # ZeRO stage、精度、batch 等全在这里配
)
```

```json
// ds_config.json
{
  "zero_optimization": {
    "stage": 2  // 改这一个数字就能在 ZeRO-1/2/3 之间切换
  },
  "bf16": { "enabled": true },
  "train_batch_size": 32
}
```

和 HuggingFace Trainer 深度集成后更简单——传一个 `deepspeed` 参数即可：

```bash
deepspeed --num_gpus=4 train.py --deepspeed ds_config.json
```

**这种"改配置不改代码"的设计**是 DeepSpeed 能在中小团队快速普及的关键原因。

#### DeepSpeed 的局限

DeepSpeed 的 ZeRO 本质上还是**数据并行的增强**——每张卡仍然在执行完整层的计算，只是存储被分摊了。ZeRO-3 在前向传播时需要 AllGather 收集完整参数、计算完再释放，通信量是 DDP 的 1.5 倍（$3\Psi$ vs $2\Psi$）。

当模型大到**单层的矩阵乘法就放不下一张卡**时（比如 70B 模型的某个线性层权重是 $[8192, 28672]$，FP16 下就要 ~440MB，加上激活值和梯度远不止这些），ZeRO 的"收集完整参数 → 计算 → 释放"策略行不通了——因为你收集回来的完整参数在 GPU 显存里放不下。

这时就需要 Megatron-LM 的 Tensor Parallelism——**不收集完整参数，直接在分片上算**。

### Megatron-LM（NVIDIA）

#### 核心贡献：Tensor Parallelism

Megatron-LM 的 TP 技术原理已经在第六节详细讲过（列切分、行切分、f/g 操作符）。这里补充框架视角。

Megatron-LM 是一个**高性能训练框架**，围绕"把计算切开、把通信优化到极致"展开：

| 模块 | 解决什么 | 对应技术 |
|------|---------|---------|
| **Tensor Parallelism** | 单层太大放不下一张卡 | 列切分 + 行切分（第六节详述） |
| **Sequence Parallelism** | TP 区域外的激活值冗余 | LayerNorm/Dropout 沿序列维度切分（第七节详述） |
| **Pipeline Parallelism** | 跨节点切分模型 | 1F1B、Interleaved 1F1B 调度（第八节详述） |
| **Context Parallelism** | 超长序列训练 | Ring Attention（第九节详述） |
| **Expert Parallelism** | MoE 专家分布 | AlltoAll 路由（第十节详述） |
| **Distributed Optimizer** | 优化器状态冗余 | 类似 ZeRO-1 的优化器分片 |
| **TransformerEngine** | 低精度训练加速 | FP8 训练（和 NVIDIA GPU 深度绑定） |

#### 为什么说 Megatron "难用"？

和 DeepSpeed 的"改配置"不同，Megatron 要求你**用它的方式写模型**。它不是一个即插即用的库，而是一个**完整的训练框架**——你需要把模型代码按照 Megatron 的 API 重写：

```python
# Megatron 要求你用它的 ColumnParallelLinear / RowParallelLinear
# 替代 PyTorch 的 nn.Linear
from megatron.core.tensor_parallel import (
    ColumnParallelLinear,  # 列切分线性层
    RowParallelLinear,     # 行切分线性层
)

class MegatronMLP(nn.Module):
    def __init__(self, config):
        # 第一个 Linear：列切分（输出维度切 N 份）
        self.gate_proj = ColumnParallelLinear(
            config.hidden_size,
            config.intermediate_size,
            gather_output=False,  # 不收集，直接传给下一层
        )
        # 第二个 Linear：行切分（输入维度切 N 份）
        self.down_proj = RowParallelLinear(
            config.intermediate_size,
            config.hidden_size,
            input_is_parallel=True,  # 输入已经是分片的
        )
```

对比 DeepSpeed 的"包一层就完事"，Megatron 要求你理解 TP 的切分逻辑，知道哪个层该列切分、哪个该行切分、中间结果的通信模式是什么。**门槛高，但换来的是通信效率的极致优化**——每一次 AllReduce 的时机和数据量都是精心设计的。

#### Megatron 针对 NVIDIA 硬件深度优化

Megatron 是 NVIDIA 自己的项目，和 NVIDIA 硬件的绑定极深：

- **NVLink/NVSwitch**：TP 的 AllReduce 通信走节点内 NVLink（~900 GB/s），这就是为什么 TP 度数通常等于节点内 GPU 数（8）
- **NCCL**：通信后端直接用 NVIDIA 的 NCCL 库，kernel 级优化
- **TransformerEngine**：NVIDIA 的 FP8 训练库，和 Megatron 原生集成，利用 H100 的 FP8 Tensor Core
- **CUDA Graph**：减少 kernel launch 开销

这种硬件绑定意味着 Megatron 在 NVIDIA GPU 上的性能几乎是天花板——但也意味着它基本不支持非 NVIDIA 硬件（AMD、华为昇腾等）。

### 核心差异对比

| 维度 | DeepSpeed | Megatron-LM |
|------|-----------|-------------|
| **来自** | 微软 | NVIDIA |
| **核心技术** | ZeRO（显存优化） | Tensor Parallelism（计算切分） |
| **解决什么** | "存不下"——显存冗余消除 | "算不动"——单层计算量太大 |
| **切分什么** | 存储的数据（optimizer states / gradients / parameters） | 计算本身（矩阵乘法切成小块） |
| **通信模式** | 用时 AllGather 收集，用完释放 | 每层前向/反向各做一次 AllReduce |
| **侵入性** | 低（包一层 + JSON 配置） | 高（需要用 Megatron API 重写模型） |
| **HuggingFace 集成** | 原生支持 | 需要额外适配（如 Megatron-LM 格式的 checkpoint 转换） |
| **硬件绑定** | 较低（也支持 AMD ROCm） | 极高（深度绑定 NVIDIA CUDA/NVLink/NCCL） |
| **适合规模** | 几张~几百张卡 | 几十张~几万张卡 |
| **适合谁** | 中小团队快速上手 | 大厂追求极致性能 |

### 组合使用：Megatron-DeepSpeed

**关键洞察：DeepSpeed 和 Megatron 不是竞品，而是解决不同维度的问题，可以组合。**

```
DeepSpeed ZeRO → 优化数据并行维度的显存
Megatron TP    → 优化单层计算的并行
Megatron PP    → 优化跨节点的层间切分

三者正交，可以同时用：

  节点内 8 卡：Megatron TP=8（单层切 8 份，NVLink 高速通信）
  4 个节点串联：Megatron PP=4（32 层分 4 段，点对点传激活值）
  32 路数据并行：DeepSpeed ZeRO-1（每路各跑不同 batch，优化器分片存储）
  → 8 × 4 × 32 = 1024 张 GPU
```

这就是第十四节说的 **3D 并行**，实际上就是 Megatron 管 TP+PP，DeepSpeed 管 DP 层的 ZeRO 优化。

**Megatron-DeepSpeed** 是微软和 NVIDIA 合作的开源项目，把两家的技术整合到一起。以下是使用它的知名模型：

| 模型 | 参数量 | 训练框架 | 并行配置 |
|------|--------|---------|---------|
| **BLOOM**（BigScience） | 176B | Megatron-DeepSpeed | TP=4, PP=12, DP=16（ZeRO-1） |
| **Falcon**（TII） | 180B | Megatron-DeepSpeed 变体 | 类似 |
| **GPT-NeoX**（EleutherAI） | 20B | Megatron-DeepSpeed | TP=2, PP=4, DP=8 |

**而像 LLaMA、DeepSeek 这些大厂的旗舰模型，通常用自研框架**（Meta 的内部框架基于 PyTorch FSDP、DeepSeek 的 HAI-LLM），但底层的 TP/PP/DP 概念完全一致。面试时重要的不是"用了哪个框架"，而是理解这三种并行策略各自解决什么问题、怎么组合。

### 还有哪些框架？

DeepSpeed 和 Megatron 是最有影响力的两个，但不是全部。补充几个值得了解的：

| 框架 | 来自 | 特点 |
|------|------|------|
| **PyTorch FSDP** | Meta / PyTorch | PyTorch 原生的 ZeRO-3 实现，第四节已讲。LLaMA 3 就用它做 DP 层 |
| **Colossal-AI** | 新加坡国立 / 潞晨科技 | 类似 Megatron-DeepSpeed 的整合框架，API 更友好 |
| **HAI-LLM** | DeepSeek 自研 | DeepSeek V3 的训练框架，包含 DualPipe、FP8 训练、辅助 loss-free 负载均衡等自研技术 |
| **Pai-Megatron-Patch** | 阿里 | 在 Megatron-LM 基础上适配 Qwen 等模型的补丁集 |
| **veScale** | 字节跳动 | PyTorch 原生的分布式训练框架，支持 4D 并行 |

### 选型决策树

```
你要训多大的模型？
│
├── <1B（如 MiniMind 64M）
│   → 单卡或 DDP 就够了，不需要任何框架
│
├── 1B~7B
│   → DeepSpeed ZeRO-2/3 或 FSDP
│   → 选择依据：用 HuggingFace 就选 DeepSpeed（集成最好）
│                用纯 PyTorch 就选 FSDP（原生支持）
│
├── 7B~70B
│   ├── 全参训练 → DeepSpeed ZeRO-3 + 多卡
│   ├── LoRA/QLoRA 微调 → DeepSpeed ZeRO-2 + 单卡/少量卡
│   └── 追求极致性能 → Megatron-LM TP + DeepSpeed ZeRO
│
└── 70B+
    → 必须 3D 并行：Megatron TP（节点内）+ PP（跨节点）+ ZeRO/FSDP（DP 层）
    → 大厂通常自研框架，但概念一致
```

## 五、混合精度训练

### 为什么需要混合精度？

FP32 每个参数 4 字节，前向和反向传播中的矩阵乘法消耗大量显存和计算。现代 GPU（Volta 及以后）的 Tensor Core 可以用 FP16/BF16 做矩阵乘法，速度是 FP32 的 2-8 倍。

混合精度的目标：**用低精度做计算密集的部分（矩阵乘法），用高精度保持数值稳定（参数更新），兼顾速度和精度。**

### 浮点格式对比

| 格式 | 总位数 | 符号位 | 指数位 | 尾数位 | 动态范围 | 精度 |
|------|--------|--------|--------|--------|---------|------|
| FP32 | 32 | 1 | 8 | 23 | $\pm 3.4 \times 10^{38}$ | 高 |
| FP16 | 16 | 1 | 5 | 10 | $\pm 65504$ | 中 |
| BF16 | 16 | 1 | 8 | 7 | $\pm 3.4 \times 10^{38}$ | 低 |
| FP8 E4M3 | 8 | 1 | 4 | 3 | $\pm 448$ | 很低 |
| FP8 E5M2 | 8 | 1 | 5 | 2 | $\pm 57344$ | 极低 |

**关键区别**：指数位决定动态范围，尾数位决定精度。

- **FP16**：5 位指数 → 动态范围窄（最大 65504），小梯度容易**下溢**（underflow，变成 0）
- **BF16**：8 位指数 → 和 FP32 相同的动态范围，但精度低（7 位尾数 vs FP32 的 23 位）
- **FP8 E4M3**：用于前向/反向的矩阵乘法操作数
- **FP8 E5M2**：动态范围更大，用于梯度表示

### 混合精度训练流程

```
┌─────────────────────────────────────────────────────────┐
│                    混合精度训练一步                        │
│                                                          │
│  FP32 Master Weights ──(cast to FP16/BF16)──→ FP16 参数  │
│                                                  │       │
│                                          前向传播（FP16）  │
│                                                  │       │
│                                              FP16 Loss   │
│                                                  │       │
│                              ×loss_scale (仅 FP16 需要)   │
│                                                  │       │
│                                          反向传播（FP16）  │
│                                                  │       │
│                                             FP16 梯度    │
│                                                  │       │
│                              ÷loss_scale + 检查 inf/nan  │
│                                                  │       │
│  FP32 Master Weights ←──(FP32 optimizer step)──  FP32 梯度│
│         更新                                              │
└─────────────────────────────────────────────────────────┘
```

**为什么需要 FP32 Master Weights？**

优化器更新是 `w = w - lr * grad`。如果 $w = 1.0$，$\text{lr} \times \text{grad} = 0.0001$：
- FP32 下：$1.0 - 0.0001 = 0.9999$（正确）
- FP16 下：$1.0 - 0.0001 \approx 1.0$（精度不够，更新被吞掉）

所以必须在 FP32 精度下做参数更新，然后 cast 回 FP16 做下一步的前向传播。

### Loss Scaling：为什么 FP16 需要，BF16 不需要

**FP16 的问题**：5 位指数 → 最小正规格化数约 $6.1 \times 10^{-5}$（$2^{-14}$；再往下是 subnormal 数，最小 $6 \times 10^{-8}=2^{-24}$，但精度已严重损失）。训练中很多梯度的绝对值小于 $6.1\times10^{-5}$（尤其是深层网络的早期层），直接下溢为 0，导致训练不收敛。

**Loss Scaling 的做法**：

1. 在反向传播前，把 loss 乘以一个大数（如 1024）
2. 反向传播得到的梯度也被放大了 1024 倍，小梯度不再下溢
3. 优化器更新前，梯度除以 1024 恢复原始大小

**动态 Loss Scaling**：自动调整缩放因子。初始值很大（如 $2^{16}$），如果梯度出现 inf/nan，说明缩放太大，减半；如果连续多步没有 inf/nan，翻倍。

MiniMind 中的实现：

```python
# trainer/train_pretrain.py:137
scaler = torch.cuda.amp.GradScaler(enabled=(args.dtype == 'float16'))
#                                  ↑ 只在 FP16 时启用，BF16 不需要

# 训练循环中:
scaler.scale(loss).backward()       # loss 乘以 scale factor
scaler.unscale_(optimizer)           # 梯度除以 scale factor
scaler.step(optimizer)               # 更新参数（如果梯度有 inf/nan 则跳过）
scaler.update()                      # 动态调整 scale factor
```

**BF16 不需要 Loss Scaling**：8 位指数给了和 FP32 相同的动态范围（$\pm 3.4 \times 10^{38}$），小梯度不会下溢。所以 BF16 混合精度训练更简单，不需要 GradScaler。这也是为什么 BF16 成为大模型训练的主流选择。

### FP8 训练：不只是预训练，而是全阶段通用

FP8 不是某个阶段专属的技术——DeepSeek-V3 在**预训练 + SFT + RL 全阶段**都用了 FP8。只要有 Linear 层的矩阵乘法（GEMM），就能用 FP8 加速。

**为什么要 FP8？** BF16 已经省了一半显存和带宽，FP8 再省一半。在 Hopper（H100/H800）上，FP8 Tensor Core 的算力是 BF16 的 2 倍（~990 TFLOPS vs ~495 TFLOPS）。

**业界各家 FP8 使用情况**：

| 模型 | 预训练 | SFT | RL | 备注 |
|------|--------|-----|-----|------|
| DeepSeek-V3 | FP8 | FP8 | FP8 | 全阶段 FP8，先驱者 |
| LLaMA 4 | FP8 | 未明确 | 未明确 | Meta 确认用了 FP8 训练 |
| GLM-5 | 标准精度（华为昇腾） | INT4 QAT | FP8 仅 rollout 推理 | 训练不用 FP8，推理用 |
| Kimi K2.5 | 未公开 | INT4 QAT | 未公开 | 量化感知训练 |

> GLM-5 不用 FP8 训练可能和硬件有关——它在华为昇腾（Ascend）上训练，昇腾对 FP8 训练的支持不如 H100 成熟。

#### 哪些操作用 FP8，哪些不用

不是所有操作都用 FP8——只有**计算密集的矩阵乘法**（GEMM）用 FP8，对精度敏感的操作仍用 BF16/FP32：

| 操作 | 精度 | 原因 |
|------|------|------|
| **Linear 层前向传播**（Fprop） | FP8 | 计算密集，GEMM 是主要开销 |
| **Linear 层激活值梯度**（Dgrad） | FP8 | 同上 |
| **Linear 层权重梯度**（Wgrad） | FP8 | 同上 |
| 激活值缓存（给反向传播用） | FP8 | 大幅节省显存 |
| MoE Expert 间的通信激活值 | FP8 | 减少通信带宽 |
| Embedding 层 | BF16 | 查表操作，不是 GEMM |
| 输出层（LM Head） | BF16 | 对最终概率分布精度敏感 |
| Attention（softmax 之后） | BF16 | softmax 对精度敏感 |
| RMSNorm | BF16/FP32 | 归一化对精度敏感 |
| MoE 门控（Router） | BF16 | 专家路由决策需要精度 |
| 主权重（master weights） | FP32 | 优化器更新需要高精度 |

> **关键洞察**：FP8 只用在最吃算力的地方（矩阵乘），其他操作保持高精度。思路和 BF16 混合精度一样——把"能用低精度的"尽量降低，"必须高精度的"保持不变。

#### 核心难题：细粒度量化（Fine-Grained Quantization）

FP8 E4M3 能表示的最大值只有 448，精度只有约 1 位有效数字。直接对整个 tensor 用一个 scale factor 做量化，异常值（outlier）会导致大量信息丢失。

先理解量化的基本操作：

```
scale = max(|所有要量化的值|) / 448      ← 448 是 FP8 E4M3 能表示的最大值
量化:   q = round(x / scale)             ← 把原始值缩放到 FP8 范围再取整
反量化: x' = q × scale                   ← 用的时候乘回来（有精度损失）
```

**问题：整个矩阵用一个 scale（tensor-wise）会怎样？**

假设权重矩阵值大多在 0.01~0.03，但有一个 outlier = 50.0：

```
scale = 50.0 / 448 = 0.1116

原始值 0.01 → round(0.01 / 0.1116) = round(0.09) = 0  → 反量化 = 0.0    ← 丢了！
原始值 0.02 → round(0.02 / 0.1116) = round(0.18) = 0  → 反量化 = 0.0    ← 丢了！
原始值 0.03 → round(0.03 / 0.1116) = round(0.27) = 0  → 反量化 = 0.0    ← 丢了！
原始值 50.0 → round(50.0 / 0.1116) = round(448)  = 448 → 反量化 = 50.0   ← 没问题

一个 outlier 把 scale 撑到 0.1116 → 0.01~0.03 的正常值全部量化成 0 → 信息全丢
```

**解决：切成小块，每块独立算 scale（fine-grained）**

DeepSeek-V3 把矩阵按小块切开，每个块各自计算 scale：

```
Block A（不含 outlier 的区域，值域 [0.01, 0.03]）:
  scale = 0.03 / 448 = 0.0000670

  0.01 → round(0.01 / 0.0000670) = round(149) = 149 → 反量化 = 0.00998  ✓
  0.02 → round(0.02 / 0.0000670) = round(299) = 299 → 反量化 = 0.02003  ✓
  0.03 → round(0.03 / 0.0000670) = round(448) = 448 → 反量化 = 0.03002  ✓
  每个值都用满了 FP8 的 0~448 表示范围，精度很好

Block B（含 outlier 的区域，值域 [0.01, 50.0]）:
  scale = 50.0 / 448 = 0.1116
  这个块里的小值确实还是会丢精度
  → 但 outlier 的"污染范围"被限制在这一个块里，不是整个矩阵
```

DeepSeek-V3 的分块策略：

| 量化对象 | 分块方式 | 块大小 | 直觉 |
|---------|---------|-------|------|
| 激活值 | 1×128 tile | 每 token 每 128 通道 | 不同 token 的激活值范围差异大，按 token 切更合理 |
| 权重 | 128×128 block | 每 128 输入 × 128 输出通道 | 权重相对稳定，大块就够 |

代价：每个 block 多存一个 scale factor。4096×4096 矩阵切成 128×128 块 = 1024 个 block → 多存 4KB，相比矩阵本身（16MB）可以忽略。

#### FP32 累加——解决 H800 硬件精度不足

H800/H100 的 Tensor Core 做 FP8×FP8 乘法时，内部累加器只有 14 位精度。当连续做 32 次以上乘加时，累积误差超过可接受范围。

DeepSeek-V3 的解决方案：每累加 $N_C = 128$ 个元素，就把中间结果**搬到 CUDA Core 上用 FP32 做一次精确累加**：

```
FP8 GEMM 的执行流程:

  Tensor Core:                    CUDA Core:
  ┌────────────────┐              ┌────────────────┐
  │ FP8 × FP8      │              │                │
  │ 累加 128 个元素  │──拷贝到──→   │  FP32 精确累加  │
  │ (14-bit 累加器) │              │                │
  └────────────────┘              └────────────────┘
  │ 继续下一组 128   │              │  累计所有组     │
  └────────────────┘              └────────────────┘

  最终结果 = 所有组的 FP32 累加值
```

```
传统混合精度:           DeepSeek V3 FP8:
BF16 参数               FP8 参数（per-128x128-block 量化）
BF16 激活值             FP8 激活值（per-1x128-tile 量化）
BF16 GEMM              FP8 GEMM + FP32 部分累加
FP32 master weights     FP32 master weights（不变）
FP32 optimizer          FP32 optimizer（不变）
```

#### 效果与适用性

**精度损失 < 0.25%**：DeepSeek 在两个规模上验证，FP8 vs BF16 的 loss 相对误差始终低于 0.25%，完全在训练随机性的可接受范围内。这也是 DeepSeek-V3 整个 14.8T tokens 训练"未遇到不可恢复的 loss spike"的技术原因。

**MiniMind 不需要 FP8**——64M 参数在一张 RTX 4060 上几小时就训完，瓶颈不在算力。FP8 是大规模训练（几百 B 参数 + 万亿级 tokens）的工程优化。

> **面试话术**："DeepSeek-V3 的 FP8 混合精度不是简单把精度降到 8 位——它用了细粒度量化，对激活值按 1×128 tile、对权重按 128×128 block 分别计算 scale factor，解决了异常值导致精度丢失的问题。同时在 GEMM 内部每累加 128 个元素就搬到 CUDA Core 做 FP32 精确累加，绕过了 H800 Tensor Core 14 位累加器精度不足的硬件限制。最终 loss 偏差 < 0.25%，几乎无损，但算力翻倍。FP8 不只用在预训练——DeepSeek-V3 全阶段（预训练 + SFT + RL）都用了 FP8。"

### 显存节省量化分析

以 1B 参数模型 + Adam 为例：

| 组件 | FP32 | FP16/BF16 混合精度 | FP8 混合精度 |
|------|------|-------------------|-------------|
| 前向参数 | 4 GB | 2 GB | 1 GB |
| 梯度 | 4 GB | 2 GB | 2 GB（通常仍用 BF16） |
| Master weights | — | 4 GB | 4 GB |
| Adam m | 4 GB | 4 GB | 4 GB |
| Adam v | 4 GB | 4 GB | 4 GB |
| **合计** | **16 GB** | **16 GB** | **15 GB** |

混合精度对 optimizer states 没有影响（始终 FP32），主要省在**激活值**上：FP16/BF16 激活值的显存是 FP32 的一半，FP8 是四分之一。对于 batch size 大、序列长的训练，激活值往往是显存的最大头。

## 六、Tensor Parallelism（张量并行）

### 为什么需要张量并行？

当模型大到一张卡放不下时，DDP 和 ZeRO 都失效了（ZeRO-3 虽然参数分片但计算时还是要 AllGather 完整参数）。Tensor Parallelism 的目标：**把单层的矩阵运算切分到多张卡上并行计算，每卡只需要存储和计算参数的一个分片。**

### Megatron-LM 的列切分和行切分

Tensor Parallelism（TP）由 Megatron-LM（NVIDIA）提出，核心思想是把线性层的权重矩阵切分到多张卡：

#### 列切分（Column Parallel）

$$Y = XA, \quad A \in \mathbb{R}^{d \times k}$$

把 $A$ 按列切成 $N$ 份：$A = [A_1 \mid A_2 \mid \ldots \mid A_N]$，每个 $A_i \in \mathbb{R}^{d \times k/N}$。

```
输入 X: [batch, seq, d]（所有卡相同）

GPU 0: Y₀ = X × A₀   → [batch, seq, k/N]
GPU 1: Y₁ = X × A₁   → [batch, seq, k/N]
...
GPU N: Yₙ = X × Aₙ   → [batch, seq, k/N]

结果: Y = [Y₀ | Y₁ | ... | Yₙ]  → [batch, seq, k]
```

每卡只存 $A_i$（$d \times k/N$ 参数），计算量也只有 $1/N$。输入 $X$ 不需要通信（每卡都有完整输入）。

#### 行切分（Row Parallel）

$$Y = XA, \quad A \in \mathbb{R}^{k \times d}$$

把 $A$ 按行切成 $N$ 份。对应地，输入 $X$ 也需要按列切分（每卡持有 $X$ 的一部分列）：

$$X = [X_1 \mid X_2 \mid \ldots \mid X_N], \quad A = \begin{bmatrix} A_1 \\ A_2 \\ \vdots \\ A_N \end{bmatrix}$$

```
GPU 0: Y₀ = X₀ × A₀   → [batch, seq, d]
GPU 1: Y₁ = X₁ × A₁   → [batch, seq, d]
...
结果: Y = Y₀ + Y₁ + ... + Yₙ  → AllReduce(sum)
```

每卡计算得到的 $Y_i$ 是部分和，需要 **AllReduce** 求和得到最终结果。

### MLP 层的 TP 切法

Transformer 的 MLP（以 MiniMind 的 SwiGLU 为例）包含两个线性变换：

```
MLP: X → Linear₁(X) × SiLU(Linear_gate(X)) → Linear₂(·) → Output
     d → 4d (或 hidden_dim)                    → d
```

Megatron-LM 的精妙之处：**第一个 Linear 列切分，第二个 Linear 行切分**，这样中间的激活值不需要通信：

```
                  GPU 0                          GPU 1
输入 X ─────────→ 列切分 Linear₁               列切分 Linear₁
[batch,seq,768]   → [batch,seq,hidden/2]         → [batch,seq,hidden/2]
                  ↓ SwiGLU（各卡独立）            ↓ SwiGLU
                  → [batch,seq,hidden/2]         → [batch,seq,hidden/2]
                  行切分 Linear₂                 行切分 Linear₂
                  → [batch,seq,768]              → [batch,seq,768]
                  └────────── AllReduce(sum) ──────────┘
                               ↓
                         [batch,seq,768]
```

**为什么中间不需要通信？** 列切分的输出 $[Y_0 \mid Y_1]$ 正好可以直接作为行切分的输入——行切分需要输入按列切分，而列切分的输出恰好就是这样的。

整个 MLP 层只需要 **1 次 AllReduce**（在行切分 Linear 之后）。

### Attention 层的 TP 切法

Attention 的 Q/K/V 投影天然按 head 维度切分：

```
以 MiniMind 参数为例: dim=768, n_heads=8, head_dim=96

2 卡 TP:
GPU 0: Q/K/V 投影，负责 head 0-3 → [batch, seq, 4, 96]
GPU 1: Q/K/V 投影，负责 head 4-7 → [batch, seq, 4, 96]

各卡独立计算 attention:
GPU 0: Attention(Q₀, K₀, V₀) → [batch, seq, 4×96=384]
GPU 1: Attention(Q₁, K₁, V₁) → [batch, seq, 4×96=384]

Output 投影（行切分）:
GPU 0: O₀ = concat(head0-3) × W_o₀ → [batch, seq, 768]
GPU 1: O₁ = concat(head4-7) × W_o₁ → [batch, seq, 768]
Y = AllReduce(O₀ + O₁)
```

同样，整个 Attention 层只需要 **1 次 AllReduce**。

### f 和 g 操作符

Megatron-LM 论文中用 $f$ 和 $g$ 两个操作符来描述 TP 中的通信模式：

| 操作符 | 前向传播 | 反向传播 |
|--------|---------|---------|
| $f$ | Identity（不通信） | AllReduce |
| $g$ | AllReduce | Identity（不通信） |

$f$ 放在列切分 Linear 之前（前向不需要通信，反向需要 AllReduce 梯度）。$g$ 放在行切分 Linear 之后（前向 AllReduce 合并结果，反向不需要通信）。

一个 Transformer Block 的前向传播中，$f$ 和 $g$ 各出现一次（Attention 后和 MLP 后各一次 AllReduce），所以**每层总共 2 次 AllReduce**。

### 为什么 TP 必须在节点内？

TP 的通信发生在**每一层的前向和反向传播中**，通信频率极高。如果跨节点做 TP，每层都要走 InfiniBand（~50 GB/s），训练速度会严重下降。

节点内有 NVLink/NVSwitch（H100 节点内 ~900 GB/s），通信延迟和带宽都远好于节点间。所以 TP 的度数通常等于节点内 GPU 数：

- 8 卡 A100/H100 节点 → TP=8（最常见）
- DGX H100 NVSwitch 节点 → TP=8

## 七、Sequence Parallelism（序列并行）

### 为什么需要 Sequence Parallelism？

Tensor Parallel 切分了 Attention 和 MLP 中的线性层。但 Transformer Block 还有 **LayerNorm** 和 **Dropout**——这些操作不是矩阵乘法，不能用 TP 切分。在 TP 中，LayerNorm 和 Dropout 的激活值在每张卡上都是完整的（$[batch, seq, dim]$），没有被分摊。

对于长序列和大 batch，这些"非 TP 区域"的激活值显存可能很可观。

### Sequence Parallelism 的做法

Megatron-LM 的 Sequence Parallelism（SP）把 **非 TP 区域**（LayerNorm、Dropout、残差连接）的激活值沿 sequence 维度切分：

```
Transformer Block 数据流（TP=2, SP 启用）:

                  ┌──── Sequence Parallel 区域 ────┐
                  │                                 │
输入激活值         │  LayerNorm + Dropout             │
[batch,seq/2,dim] │  每卡只持有 seq/2 的激活值        │
（每卡持有一半序列）│                                 │
                  └────────────┬────────────────────┘
                               │
                          AllGather
                         （收集完整序列）
                               │
                  ┌──── Tensor Parallel 区域 ───────┐
                  │                                  │
                  │  Attention / MLP                  │
                  │  每卡持有 dim/2 的参数             │
                  │  输入是完整序列 [batch,seq,dim]     │
                  │                                  │
                  └────────────┬─────────────────────┘
                               │
                         ReduceScatter
                      （归约 + 按序列分片）
                               │
                  ┌──── Sequence Parallel 区域 ────┐
                  │                                 │
                  │  残差连接 + LayerNorm             │
                  │  [batch,seq/2,dim]               │
                  └─────────────────────────────────┘
```

**通信变化**：原来 TP 用的是 AllReduce（= ReduceScatter + AllGather），SP 把 AllReduce 拆开了——ReduceScatter 放在 TP 区域出口（顺便把激活值按序列切分），AllGather 放在 TP 区域入口（收集完整序列）。**总通信量不变**，但非 TP 区域的激活值显存减少为 $1/N$。

### SP vs CP（后面会讲）

| | Sequence Parallelism | Context Parallelism |
|---|---|---|
| 切什么 | 非 TP 区域的激活值 | 整个输入序列和所有激活值 |
| 目的 | 减少 TP 中非切分区域的激活值显存 | 支持超长序列（128K+）训练 |
| 配合 | 必须和 TP 一起用 | 独立于 TP |
| 通信 | AllGather / ReduceScatter | Ring Attention |
| 谁提出 | Megatron-LM | Megatron-LM / Meta |

## 八、Pipeline Parallelism（流水线并行）

### 为什么需要流水线并行？

TP 切分单层的矩阵运算，但通信密集（每层 2 次 AllReduce），只适合高带宽的节点内。当节点数很多时，需要另一种切法——**按层切分**，不同层放不同节点。层与层之间只传递激活值（点对点通信），通信量小，适合节点间低带宽链路。

### 朴素流水线的 Bubble 问题

把 $L$ 层模型分成 $P$ 个 stage，每个 stage 放一组 GPU：

```
4 个 stage（P=4），1 个 micro-batch:

时间 →
Stage 0: [  F  ]                              [  B  ]
Stage 1:        [  F  ]                [  B  ]
Stage 2:               [  F  ]  [  B  ]
Stage 3:                     [FB]

大量空闲时间（bubble）：每个 stage 大部分时间在等
```

Bubble 占比 = $(P-1)/P$。4 个 stage 时 75% 的时间在空闲。

### GPipe：微批次填充流水线

GPipe 把一个 batch 拆成 $M$ 个 micro-batch，交错送入流水线：

```
4 个 stage，4 个 micro-batch（M=4）:

时间 →
Stage 0: [F₁][F₂][F₃][F₄]                         [B₄][B₃][B₂][B₁]
Stage 1:     [F₁][F₂][F₃][F₄]                 [B₄][B₃][B₂][B₁]
Stage 2:          [F₁][F₂][F₃][F₄]        [B₄][B₃][B₂][B₁]
Stage 3:               [F₁][F₂][F₃][F₄][B₄][B₃][B₂][B₁]
                                        ↑
                                   pipeline flush
                              （等所有前向完成才开始反向）
```

$$\text{Bubble 比例} = \frac{P - 1}{M + P - 1}$$

$M=4, P=4$ 时 bubble = 3/7 ≈ 43%。$M=32, P=4$ 时 bubble = 3/35 ≈ 8.6%。micro-batch 越多 bubble 越小。

**GPipe 的缺点**：所有前向完成后才开始反向（synchronous flush），需要同时存储 $M$ 个 micro-batch 的激活值，显存峰值高。

### 1F1B（One Forward One Backward）

1F1B 在稳态阶段交替执行一个前向和一个反向，减少峰值显存：

```
4 个 stage，8 个 micro-batch:

Stage 0: [F₁][F₂][F₃][F₄][B₁][F₅][B₂][F₆][B₃][F₇][B₄][F₈][B₅][B₆][B₇][B₈]
Stage 1:     [F₁][F₂][F₃][B₁][F₄][B₂][F₅][B₃][F₆][B₄][F₇][B₅][F₈][B₆][B₇][B₈]
Stage 2:          [F₁][F₂][B₁][F₃][B₂][F₄][B₃][F₅][B₄][F₆][B₅][F₇][B₆][F₈][B₇][B₈]
Stage 3:               [F₁][B₁][F₂][B₂][F₃][B₃][F₄][B₄][F₅][B₅][F₆][B₆][F₇][B₇][F₈][B₈]
                  warmup  │      steady state（1F1B）        │  cooldown
```

**稳态阶段**：每做完一个前向就做一个反向。完成反向后就可以释放该 micro-batch 的激活值，所以峰值显存 ≈ $P$ 个 micro-batch 的激活值（而 GPipe 是 $M$ 个）。

**Bubble 比例仍然是 $(P-1)/(M+P-1)$**，和 GPipe 相同。1F1B 的优势在显存，不在 bubble。

### Interleaved 1F1B（Virtual Pipeline Parallelism, VPP）

让每个 stage 不再持有连续的层，而是**多个不连续的层块**。例如 16 层、4 stage：

```
普通 PP:  Stage 0 = Layer 0-3,  Stage 1 = Layer 4-7,  Stage 2 = Layer 8-11, Stage 3 = Layer 12-15

VPP (v=2):
Stage 0 = Layer 0-1 + Layer 8-9    （2 个 virtual stage，每个 2 层）
Stage 1 = Layer 2-3 + Layer 10-11
Stage 2 = Layer 4-5 + Layer 12-13
Stage 3 = Layer 6-7 + Layer 14-15
```

一个 micro-batch 在每个物理 stage 上停留 $v$ 次（$v$ = virtual stages 数），pipeline 深度从 $P$ 变成 $P/v$。

$$\text{Bubble 比例} = \frac{P/v - 1}{M + P/v - 1}$$

$v=2$ 时 bubble 减半。代价是通信次数增加（每个 micro-batch 经过更多 stage 间的传递）。

### Zero-Bubble PP

反向传播的计算可以分解为两个独立的操作：

- **B（backward for input）**：计算输入的梯度，传给前一个 stage
- **W（backward for weight）**：计算权重的梯度，用于优化器更新

$B$ 必须在 $B$ 的依赖链上立即执行（前一层需要它的结果来继续反向传播），但 $W$ 只需要在 optimizer step 之前完成就行。

**Zero-Bubble 的思想**：把 $W$ 延迟执行，用它来**填充 bubble**。

```
传统 1F1B:  [F₁][F₂]...[B₁][F₃][B₂]...         ← B 包含 B+W
Zero-Bubble: [F₁][F₂]...[B₁][F₃][B₂]...[W₁][W₂]  ← B 和 W 分离，W 填 bubble
```

理论上可以完全消除 bubble（bubble → 0），代价是峰值显存增加（$W$ 延迟执行意味着梯度要多存一段时间）。

### DualPipe（DeepSeek V3）

DeepSeek V3 提出 DualPipe：**双向流水线**，从 pipeline 两端同时灌入 micro-batch。

```
传统 PP（单向）:
Stage 0 → Stage 1 → Stage 2 → Stage 3

DualPipe（双向）:
流 A: Stage 0 → Stage 1 → Stage 2 → Stage 3
流 B: Stage 3 → Stage 2 → Stage 1 → Stage 0
      （从另一端灌入，反方向流动）
```

**关键设计**：
- 最浅层（Stage 0）和最深层（Stage 3）部署在同一个 PP rank 上，实现物理参数共享
- 两个流的计算和通信可以交错重叠
- 相比 1F1B，bubble 大幅减少，且峰值激活显存只增加 $1/PP$ 倍

**适用场景**：DeepSeek V3 使用 MoE 架构，每层的 All-to-All 通信（Expert Parallel）可以和上下游层的计算重叠。DualPipe 正是为这种"计算和通信都很重"的场景设计的。

### PP 调度策略对比

| 策略 | Bubble 比例 | 峰值显存 | 通信次数 | 提出者 |
|------|-----------|---------|---------|--------|
| GPipe | $(P-1)/(M+P-1)$ | 高（$M$ 个 micro-batch 激活） | 基准 | Google 2019 |
| 1F1B | $(P-1)/(M+P-1)$ | 低（$P$ 个 micro-batch 激活） | 基准 | Microsoft 2021 |
| Interleaved 1F1B | $(P/v-1)/(M+P/v-1)$ | 低 | $v\times$ 基准 | NVIDIA 2021 |
| Zero-Bubble | 接近 0 | 中（$W$ 延迟） | 基准 | Sea AI Lab 2024 |
| DualPipe | 大幅减少 | 中（$+1/PP$） | 基准 | DeepSeek 2024 |

## 九、Context Parallelism（上下文并行）

### 为什么需要上下文并行？

训练长序列（128K+ tokens）时，Self-Attention 的激活值显存和序列长度的平方成正比：

$$\text{Attention 激活值} \propto \text{batch} \times \text{n\_heads} \times \text{seq\_len}^2$$

以 MiniMind 参数（8 heads）、seq_len=128K 为例，attention score 矩阵大小 = $8 \times 128K \times 128K \times 2B$（BF16）= **256 GB**，单卡完全放不下。

即使用 FlashAttention（Ch04a）消除了 $O(N^2)$ 的显存存储，每层激活值仍然和 seq_len 成线性关系。当 seq_len 非常长时，单卡显存还是不够。

### Context Parallelism 的做法

把输入序列沿 sequence 维度切分到 $C$ 张卡，每卡只处理 $\text{seq\_len}/C$ 长度的子序列：

```
CP=4, seq_len=128K:
GPU 0: tokens [0, 32K)         → 第 1 段
GPU 1: tokens [32K, 64K)       → 第 2 段
GPU 2: tokens [64K, 96K)       → 第 3 段
GPU 3: tokens [96K, 128K)      → 第 4 段
```

**问题**：Self-Attention 需要每个 token 关注所有其他 token。GPU 0 上的 Q 需要和 GPU 1/2/3 上的 K/V 计算 attention。怎么办？

### Ring Attention 算法

Ring Attention 把 $C$ 张卡排成环形，K/V 在环上依次传递：

```
Ring Attention（CP=4）:

Step 1: 每卡用本地 Q 和本地 K/V 计算 attention → 得到部分结果
        同时把 K/V 发给环上的下一卡

Step 2: 每卡用本地 Q 和收到的 K/V 计算 attention → 累加到部分结果
        同时继续传递 K/V

Step 3: 同上

Step 4: 所有 K/V 都转了一圈，每卡拿到完整的 attention 结果

GPU 0: Q₀×K₀V₀ → Q₀×K₃V₃ → Q₀×K₂V₂ → Q₀×K₁V₁  → 完整结果
GPU 1: Q₁×K₁V₁ → Q₁×K₀V₀ → Q₁×K₃V₃ → Q₁×K₂V₂  → 完整结果
GPU 2: Q₂×K₂V₂ → Q₂×K₁V₁ → Q₂×K₀V₀ → Q₂×K₃V₃  → 完整结果
GPU 3: Q₃×K₃V₃ → Q₃×K₂V₂ → Q₃×K₁V₁ → Q₃×K₀V₀  → 完整结果
```

每步中，K/V 的发送和 attention 计算可以重叠（compute-communication overlap），实际开销主要取决于 attention 计算时间。

### CP 和 SP 的关键区别

**Sequence Parallelism**（第七节）是 TP 的附属优化——只切分非 TP 区域的激活值，TP 区域内仍然需要完整序列。SP 的 "sequence" 指的是"沿序列维度切分激活值的存储"。

**Context Parallelism** 是独立的并行维度——整个 Transformer Block（包括 Attention 的 Q/K/V 计算）都在子序列上操作。CP 通过 Ring Attention 解决了"每个 token 需要关注所有其他 token"的问题。

### LLaMA 3 的 CP 实现

LLaMA 3 405B 训练中，CP 主要用于 128K 长序列训练阶段：
- 8K 序列训练时不启用 CP（CP=1）
- 128K 序列训练时启用 CP（论文未公开具体 CP 度数，但提到在此模式下吞吐量为 380 TFLOPS/GPU，低于 8K 时的 400 TFLOPS/GPU）

## 十、Expert Parallelism（专家并行）

### 为什么需要专家并行？

MoE（Mixture of Experts）模型的参数量远大于实际激活的参数量——DeepSeek V3 有 671B 总参数但每个 token 只激活 37B。这些"额外"的参数就是专家网络（expert），每个专家是一个独立的 FFN。

问题：专家太多，一张卡放不下所有专家。Expert Parallelism（EP）把不同的专家放到不同的 GPU 上。

### EP 的工作流程

```
EP=4，8 个专家:
GPU 0: Expert 0, 1
GPU 1: Expert 2, 3
GPU 2: Expert 4, 5
GPU 3: Expert 6, 7

一次前向传播:
1. Router 决定每个 token 应该去哪些专家
2. AlltoAll: 每个 GPU 把 token 发送到对应专家所在的 GPU
3. 各 GPU 执行本地专家的计算
4. AlltoAll: 把结果发送回 token 原来所在的 GPU
```

**通信模式**：两次 AlltoAll——token 路由过去，结果路由回来。AlltoAll 的通信量取决于路由的稀疏程度（每个 token 激活几个专家）。

### 负载均衡问题

如果所有 token 都被路由到少数专家，那些专家所在的 GPU 负载极重，其他 GPU 空闲。

**传统方案：auxiliary loss（辅助损失）**

在训练目标中加一个辅助 loss，惩罚不均匀的负载分布。问题：这个额外的 loss 会干扰主任务的优化，影响模型质量。

**DeepSeek V3 的方案：auxiliary-loss-free load balancing**

DeepSeek V3 技术报告提出了一种不使用 auxiliary loss 的负载均衡策略：
- 为每个专家维护一个 bias 项（标量），加在 router 的 logits 上
- 每步训练后，根据实际负载动态调整 bias：负载重的专家降低 bias，负载轻的升高 bias
- 不引入额外的 loss 项，不影响模型优化方向

### DeepSeek V3 的 EP 实现

- **EP 度数**：64 路专家并行（EP=64：256 个 routed experts 分布在 64 张卡上，每卡放 4 个专家）
- **DeepEP**：DeepSeek 开源的高性能 EP 通信库，优化了 AlltoAll 通信
- **通信隐藏**：DualPipe 中，EP 的 AlltoAll 通信可以和其他层的计算重叠

## 十一、通信拓扑与并行策略选择

### 硬件通信层级

```
┌─────────────────────────────────────────────────────┐
│                   GPU 集群                           │
│                                                      │
│  ┌──────── 节点 0 ────────┐  ┌──────── 节点 1 ──────┐│
│  │ GPU0 ←NVLink→ GPU1     │  │ GPU0 ←NVLink→ GPU1   ││
│  │  ↕            ↕        │  │  ↕            ↕      ││
│  │ GPU2 ←NVLink→ GPU3     │  │ GPU2 ←NVLink→ GPU3   ││
│  │  ↕            ↕        │  │  ↕            ↕      ││
│  │ GPU4 ←NVLink→ GPU5     │  │ GPU4 ←NVLink→ GPU5   ││
│  │  ↕            ↕        │  │  ↕            ↕      ││
│  │ GPU6 ←NVLink→ GPU7     │  │ GPU6 ←NVLink→ GPU7   ││
│  └──────────┬─────────────┘  └──────────┬───────────┘│
│             └──── InfiniBand / RoCE ─────┘            │
│                  （节点间，带宽低）                     │
└─────────────────────────────────────────────────────┘
```

| 通信链路 | 带宽 | 延迟 | 适合的并行策略 |
|---------|------|------|--------------|
| NVLink（节点内） | ~900 GB/s（H100 NVSwitch） | ~μs | **TP**（每层通信，频率高） |
| InfiniBand（节点间） | ~50 GB/s（NDR 400Gbps；上一代 HDR 为 200Gbps） | ~ms | **PP**（层间点对点通信，频率低）、**DP**（AllReduce 梯度，可和计算重叠） |

### 并行策略放置原则

**TP 在最内层（节点内），PP 在中间层（跨节点），DP 在最外层。**

```
示例：64 GPU = 8 节点 × 8 卡/节点

TP=8（节点内 8 卡做 Tensor Parallel）
PP=4（4 个节点串成 Pipeline，每节点 8 卡是一个 PP stage）
DP=2（2 组数据并行，每组 32 卡）

TP=8 × PP=4 × DP=2 = 64 GPU
```

**为什么这么放？**
- TP 通信量最大（每层 2 次 AllReduce），必须用最高带宽的链路（NVLink）
- PP 通信量小（层间传递激活值，点对点），跨节点可接受
- DP 的 AllReduce 可以和计算重叠，对带宽不那么敏感

## 十二、计算-通信重叠

### 为什么重要？

分布式训练中，如果计算和通信串行执行，GPU 在通信时空闲，利用率低。**让通信和计算在时间上重叠（overlap）** 是提升训练效率的核心工程优化。

### DDP 的 Gradient Bucket 重叠

已在第二节详述。DDP 把梯度按反向传播顺序分成多个 bucket，每个 bucket 填满后立即异步 AllReduce，同时继续计算其他层的梯度。

### ZeRO-3/FSDP 的 Prefetch

FSDP 在计算第 $i$ 层时，可以**提前发起第 $i+1$ 层参数的 AllGather**（prefetch），这样等第 $i$ 层计算完毕时，第 $i+1$ 层的参数已经收集好了：

```
Layer i 计算 ──→ Layer i+1 计算 ──→ Layer i+2 计算
  ↓                ↓                  ↓
  AllGather(i+1)   AllGather(i+2)     AllGather(i+3)    ← prefetch
```

代价：多存一层的完整参数（prefetch 来的），显存增加一点。

### TP 的通信重叠

在 TP + SP 的配置下，AllGather 和 ReduceScatter 可以和非通信依赖的计算重叠。例如 attention 的 Q 投影和 KV 的 AllGather 可以部分重叠。

### DualPipe 的双向重叠

DualPipe 的核心创新正是计算-通信重叠：两个流方向的前向/反向计算和 AlltoAll（EP 通信）交替安排，一个流在通信时另一个流在计算，最大化 GPU 利用率。DeepSeek V3 技术报告称其实现了"接近零"的 AlltoAll 通信开销。

## 十三、显存占用完整分析

### 模型状态显存

设参数量为 $\Psi$，使用混合精度（BF16）+ Adam 优化器：

| 组件 | 大小（bytes） | 说明 |
|------|-------------|------|
| BF16 参数 | $2\Psi$ | 前向/反向计算用 |
| BF16 梯度 | $2\Psi$ | 反向传播产生 |
| FP32 Master Weights | $4\Psi$ | 优化器持有 |
| FP32 Adam $m$ | $4\Psi$ | 一阶动量 |
| FP32 Adam $v$ | $4\Psi$ | 二阶动量 |
| **合计** | $16\Psi$ | |

### 激活值显存

Transformer 一层的激活值（不含 attention score），对 batch size $B$、序列长度 $S$、隐藏维度 $D$：

$$\text{每层激活值} \approx B \times S \times D \times (10 + \frac{24}{t}) \text{ bytes（BF16, TP 度数 } t \text{）}$$

（这里 10 来自 LayerNorm 输入/输出、残差、Q/K/V/O 各 2 bytes；$24/t$ 来自 TP 切分后的 Attention 和 MLP 中间结果。具体系数因实现而异，此为 Megatron-LM 论文的近似。）

以 MiniMind 参数（$D=768$, $L=8$ 层）、$B=32$, $S=340$, $t=1$（无 TP）：

$$\text{每层} \approx 32 \times 340 \times 768 \times 34 \approx 284\text{MB}$$

$$\text{总激活值} \approx 8 \times 284 = 2.27\text{GB}$$

### 各并行策略的显存削减

| 策略 | 模型状态削减 | 激活值削减 |
|------|-----------|----------|
| DDP | 无 | 无 |
| ZeRO-1 | Optimizer $\div N$ | 无 |
| ZeRO-2 | Optimizer + Grad $\div N$ | 无 |
| ZeRO-3/FSDP | 全部 $\div N$ | 无（计算时仍需完整） |
| TP | 参数 $\div t$、激活值部分 $\div t$ | Attention/MLP 激活 $\div t$ |
| SP | 无额外 | 非 TP 区域激活 $\div t$ |
| PP | 参数 $\div p$（只存本 stage 的层） | 本 stage 激活 |
| CP | 无 | 全部 $\div c$ |
| Gradient Checkpointing | 无 | 大幅减少（只存 checkpoint 层） |

### 数字举例：训练 1B 模型

| 配置 | 每卡显存 |
|------|---------|
| DDP，FP32 | 16 GB（模型状态）+ 激活值 |
| DDP，BF16 混合精度 | 16 GB + 激活值（省在激活值上） |
| ZeRO-2，4 卡 | 5.5 GB + 激活值 |
| ZeRO-3，4 卡 | 4 GB + 激活值 |
| TP=2 + ZeRO-2，4 卡 | 更低（参数和激活值都减半） |

## 十四、3D → 4D → 5D 并行

### 3D 并行（经典组合）

$$\text{3D} = \text{DP} \times \text{TP} \times \text{PP}$$

```
示例：64 GPU 训 175B 模型
TP = 8（节点内 8 卡）
PP = 4（4 个节点串成 pipeline）
DP = 2（2 组数据并行）
8 × 4 × 2 = 64 GPU
```

### 4D 并行（+CP）

$$\text{4D} = \text{DP} \times \text{TP} \times \text{PP} \times \text{CP}$$

LLaMA 3 405B 训练使用 4D 并行：

```
16,384 GPU（16K 张 H100）
TP = 8     （节点内 8 卡）
PP = 16    （16 个 pipeline stage）
CP = 可变  （长序列训练时启用）
DP = 128   （FSDP SHARD_GRAD_OP）

验算: 8 × 16 × 128 = 16,384 ✓ （CP 在 DP 维度内动态启用）
```

### 5D 并行（+EP）

$$\text{5D} = \text{DP} \times \text{TP} \times \text{PP} \times \text{CP} \times \text{EP}$$

适用于 MoE 模型。Megatron-LM 的最新版本支持 5D 并行，加上 Distributed Adam 和 Transformer Engine 优化。

DeepSeek V3 的配置可以理解为 3D+EP 的变体（没有使用 TP 和 CP）。

### 并行维度总结

| 维度 | 切什么 | 通信操作 | 通信频率 | 适合放在 |
|------|--------|---------|---------|---------|
| DP | 数据 | AllReduce / ReduceScatter + AllGather | 每 step 1 次 | 最外层 |
| TP | 单层权重矩阵 | AllReduce（每层 2 次） | 每层 | 节点内 |
| PP | 层 | 点对点（激活值） | 每 micro-batch | 节点间 |
| CP | 序列 | Ring Attention | 每层 Attention | 视带宽 |
| EP | 专家 | AlltoAll | 每个 MoE 层 | 视拓扑 |

**面试考点：DeepSeek V3 为什么不用 TP？**

DeepSeek V3 的 MoE 架构中，Expert Parallel 的 AlltoAll 通信已经占用了跨节点带宽。如果再加 TP，TP 的 AllReduce 也需要高带宽，两者会在带宽上竞争。DeepSeek 选择用 DualPipe（PP）来切分模型，避免 TP 的高频通信开销，同时利用 DualPipe 的计算-通信重叠来隐藏 EP 的 AlltoAll 延迟。

## 十六、面试话术

### 30 秒版（快速概览）

> 分布式训练有五种基本并行策略。数据并行（DDP/ZeRO/FSDP）复制模型到多卡，各处理不同数据分片，AllReduce 同步梯度。张量并行把单层的权重矩阵切分到多卡，适合节点内高带宽连接。流水线并行按层切分，不同层放不同节点，用微批次调度减少 bubble。上下文并行沿序列维度切分，用 Ring Attention 解决长序列训练。专家并行把 MoE 的不同专家分布到不同卡，用 AlltoAll 通信路由 token。业界大模型通常组合多种策略：LLaMA 3 用 4D 并行（TP+PP+CP+FSDP），DeepSeek V3 用 PP+EP+DP 但不用 TP——因为 EP 的 AlltoAll 已经占满了跨节点带宽。在 MiniMind 项目里我实操了 DDP，理解了 DistributedSampler、gradient bucket 通信重叠的机制。

### 60 秒版（含技术细节）

> 在 30 秒版基础上补充：
>
> 通信原语层面，分布式训练的核心操作是 AllReduce、AllGather、ReduceScatter 和 AlltoAll。Ring AllReduce 把通信量从 O(NM) 降到 O(M)，和 GPU 数无关。
>
> ZeRO 逐步消除 DDP 中的冗余：Stage 1 切 optimizer states，Stage 2 加切梯度，Stage 3 连参数也切。FSDP 是 PyTorch 原生的 ZeRO-3，LLaMA 3 选了 SHARD_GRAD_OP 模式（ZeRO-2）因为 TP+PP 已经切够小，不需要 ZeRO-3 的额外通信。
>
> 混合精度方面，BF16 和 FP32 有相同的动态范围，所以不需要 loss scaling，成为大模型训练的标准选择。DeepSeek V3 进一步用 FP8 训练，通过 per-tile 细粒度量化和 FP32 累加保持精度。
>
> 通信拓扑上，TP 放节点内（NVLink ~900GB/s），PP 放节点间（InfiniBand ~50GB/s），DP 最外层。计算-通信重叠是关键优化：DDP 的 gradient bucket、FSDP 的 prefetch、DualPipe 的双向流水线都是为了隐藏通信延迟。

### 高频追问

**Q：DDP 和 DP（DataParallel）有什么区别？**
> DP 用单进程多线程，有 GIL 瓶颈和参数 server 通信瓶颈。DDP 用多进程 + NCCL 集合通信，每卡一个进程，通过 Ring AllReduce 同步梯度，性能远好于 DP。DDP 是目前的标准做法，DP 已不推荐使用。

**Q：ZeRO-2 和 ZeRO-3 怎么选？**
> ZeRO-2 通信量和 DDP 一样（$2\Psi$），ZeRO-3 多了前向的 AllGather（$3\Psi$）。如果 GPU 显存够（配合 TP/PP），优先 ZeRO-2；显存实在不够才用 ZeRO-3。LLaMA 3 就是这个选择思路。

**Q：为什么 BF16 不需要 loss scaling？**
> BF16 有 8 位指数，动态范围和 FP32 一样大（$\pm 3.4 \times 10^{38}$），小梯度不会下溢。FP16 只有 5 位指数，最小正规格化数约 $6.1 \times 10^{-5}$（subnormal 下限 $6 \times 10^{-8}$ 精度已严重损失），很多梯度会下溢为 0，所以需要先放大再缩回。

**Q：TP 为什么不能跨节点？**
> TP 每层有 2 次 AllReduce 通信。假设 100 层模型，每步训练就是 200 次 AllReduce。跨节点 InfiniBand 带宽（~50 GB/s）远低于节点内 NVLink（~900 GB/s），延迟也高得多，训练速度会严重下降。

**Q：DeepSeek V3 为什么不用 TP？**
> MoE 模型的 Expert Parallel 需要 AlltoAll 通信，已经占用跨节点带宽。如果再加 TP 的 AllReduce，两种高频通信竞争带宽。DeepSeek 选择用 DualPipe（PP）切分模型——PP 是点对点通信，带宽需求小得多。同时 DualPipe 的双向调度可以把 EP 的 AlltoAll 和计算重叠。

**Q：Pipeline Parallel 的 bubble 怎么减少？**
> 增加 micro-batch 数量（$M$ 大了 bubble 比例 $(P-1)/(M+P-1)$ 就小了）。用 Interleaved 1F1B 让每个 stage 持有多个不连续层块，等效减少 pipeline 深度。用 Zero-Bubble 把反向拆成 B 和 W，用 W 填充 bubble。用 DualPipe 双向灌入进一步压缩。
