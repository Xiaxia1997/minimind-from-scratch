## 1. 为什么需要监控——训练 Loss 降了不代表模型变好了

新手最常犯的错：盯着 train loss 一路下降，觉得一切正常。

但 train loss 降只说明模型在**训练集**上拟合得更好——它可能在背数据（过拟合），可能只学了某些领域而忘了别的（遗忘），可能 reward 在涨但模型在 hack 评分规则（Goodhart），可能硬件出了问题算力减半你都不知道。

所以监控不是"看一个数降没降"，而是同时回答三个问题：

1. **活着没**（稳定性）：数值上是否正常运行，会不会突然崩或慢性死亡
2. **学好没**（效果）：能力是否按预期增长，算力花得值不值
3. **跑快没**（效率）：硬件是否跑满，有没有隐性减速

一个指标通常只回答其中一个问题。下面逐个讲清楚。

## 2. 核心指标逐个深讲

### 2.1 Train Loss——最基础但最容易被误读

**它在量什么**：cross-entropy loss，模型对训练数据下一个 token 的预测准确度。loss = 3.0 大致意味着模型认为正确 token 在整个词表（比如 6400）中排前 $e^3 \approx 20$ 位左右。

**正常行为**：

```
前 1%：    急剧下降（从 8+ 降到 4~5），模型在学基本词频
前 10%：   快速下降（4~5 降到 3~3.5），学语法和简单模式
中期：     缓慢下降，power-law 曲线（斜率越来越小）
后期：     接近平台期，每 10% 数据只降 0.0x
```

**什么时候它在骗你**：

| 情况 | Train loss 表现 | 真实状态 |
|---|---|---|
| 过拟合 | 稳步下降 | 但 val loss 已经在涨——模型在背数据，泛化能力在退化 |
| 能力遗忘 | 总 loss 在降 | 但某个域的 val loss 在涨——加权平均掩盖了局部退化 |
| SFT 记忆效应 | 每个 epoch 交界处 loss 突降 | 不是突然变好，是第二遍见到已学过的数据，纯记忆 |
| RL 阶段 | loss 概念变了 | reward 取代了 loss，train loss 不再是主要信号 |

**面试关键认知**：train loss 是**必要但不充分**的信号。它降了不能证明模型变好，但它不降（或升）一定说明出了问题。

### 2.2 Grad Norm——模型"想更新多少"的体温计

**它在量什么**：所有参数梯度拼成一个向量后的 L2 范数。直觉——梯度告诉优化器"往哪个方向走、走多远"。grad norm 就是"想走多远"的总量。

```python
# PyTorch 内置：计算 grad norm 的同时做裁剪
grad_norm = torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
# 返回裁剪前的原始值；如果 > max_norm 则等比缩放所有梯度
```

**健康范围**：模型训练稳定后通常在一个窄带里波动（如 0.5~2.0），具体值因模型而异，关键是**稳定**。

**异常信号**：

| 异常 | 含义 | 后果 |
|---|---|---|
| **单步暴涨**（比如从 1.0 跳到 50） | 这个 batch 产生了异常大的梯度 | 如果 clip 兜住了（grad norm 回落），伤害有限但要记录；没兜住 = 参数被推到危险位置 |
| **clip 触发率飙升**（从 5% 到 80%） | 大量 batch 都在试图做大幅更新 | lr 太高，或数据质量系统性变差 |
| **趋近于零** | 几乎不产生梯度 | 三种可能：lr 太小、参数被误冻结、DDP 梯度通信断了（静默故障） |
| **缓慢爬升** | 更新量逐渐变大 | 可能是漂移型崩溃的前兆——几百步后会以 spike 收尾 |

**Clip 触发率**：健康时 5~15%。这个比例说明偶尔有难 batch 想大步更新，被 clip 限住了——正常。>50% 说明多数 batch 都想大步走但被强行限制，训练在"刹车状态"，要降 lr。

### 2.3 Learning Rate——监控一个配置值？是的

LR 本身是你设定的 schedule，不是模型输出。为什么还要画曲线？

**因为 LR 配置 bug 是真实的事故类型**：

- warmup 步数写错（少一个零），模型用了 10 倍该用的 lr 飞了
- resume 训练后 scheduler 状态没恢复，从头开始 warmup
- cosine decay 的 T_max 参数错误，lr 提前到零
- 多个参数组用了不同 lr，merge 后搞混了

**操作**：画 lr 曲线，肉眼确认和预期一致。特别是 resume 后的第一个 checkpoint——这是最高频的 lr 事故点。

### 2.4 Validation Loss——真正衡量"模型学到了什么"

**它在量什么**：模型在**从未见过的数据**上预测下一个 token 的 loss。和 train loss 的区别——train loss 会被记忆拉低（模型可以"背答案"），val loss 不会。

**为什么一定要分域**：

假设你在训练一个通用模型，数据包含代码（40%）、通识（30%）、数学（20%）、对话（10%）。总 val loss 在降，看起来正常。但实际上：

```
代码 val loss:   3.2 → 2.8 → 2.5     ✓ 正常
通识 val loss:   3.5 → 3.3 → 3.2     ✓ 正常
数学 val loss:   4.0 → 3.8 → 4.1     ✗ 回升了！
对话 val loss:   3.0 → 2.9 → 3.3     ✗ 回升了！
总 val loss:     3.4 → 3.1 → 2.9     看起来正常（被代码和通识的下降拉低了）
```

数学和对话的能力在退化，但总 loss 完全掩盖了这个信号。**分域 val loss 是发现"慢性遗忘"的唯一手段**。

**各阶段的区别**：
- **预训练**：按数据源分（代码/通识/数学/对话……），每个源一条曲线
- **SFT**：按任务类型分（QA/摘要/翻译……），且只算 assistant 部分的 loss
- **RL**：val loss 的角色被 proxy vs gold reward 取代（见 2.9）

**Probe set**：除了普通 val set，还可以维护一个**固定不变的小样本集**（几百条），每个 checkpoint 都跑一遍。好处是跨 run、跨配置完全可比——换了数据配比、换了 lr，probe set loss 的变化直接反映影响。

### 2.5 Max Attention Logits——漂移型崩溃的提前预警

**它在量什么**：Attention 中 $QK^T / \sqrt{d}$ 的最大值。就是 softmax 的输入——这个值如果持续变大，softmax 的输出会趋近 one-hot（一个位置接近 1，其余接近 0），梯度会变得病态。

**为什么它是"慢变量之王"**：

因为它能在崩溃前**几百到几千步**就发出预警。看一个真实的演进过程：

```
训练初期：   max logits ≈ 20~30    → softmax 正常，梯度健康
训练中期：   max logits ≈ 50~80    → softmax 开始变尖，但还没崩
训练后期：   max logits ≈ 200+     → BF16 精度不够 → 突然 NaN → spike
```

如果你只看 grad norm 和 loss，你看到的是"一切正常直到突然崩了"。但如果你画了 max attention logits 曲线，你会看到它在崩溃前几百步就开始单调爬升——这是你介入的窗口。

**为什么看 max 不看 mean**：漂移通常只发生在**少数几个 head** 里。Kimi K2 的数据：全程只有 12.7% 的注意力头触发过 clip——如果你看所有 head 的均值，这个信号会被 87.3% 的正常 head 稀释掉。

**为什么会漂移——正反馈机制**：

1. 训练目标鼓励 attention 变"尖锐"（精准关注某个 token → 需要大的 logit 差）
2. Q 和 K 的权重没有约束 → logit 差变大的方式是 Q/K 的范数变大
3. 范数变大 → softmax 更尖 → 梯度更集中于被关注的 token → 进一步推高范数
4. 正反馈形成，直到数值溢出

**解决——给 Q/K 加约束**：
- **QK-Norm**（Qwen3、Gemma 3、OLMo 2、MiniMind）：对 Q 和 K 做 RMSNorm，限制范数
- **QK-Clip**（Kimi K2）：logits 超过阈值 τ 直接截断（τ=100）

> 我们在 [04-Attention](04-Attention.md) Step 3 加的 QK-Norm 就是防这个病的——不是花哨功能，是架构级预防。

### 2.6 Update/Weight Ratio——比 Grad Norm 更准的"lr 偏大"探测器

**它在量什么**：$\|\Delta W\| / \|W\|$，一步更新对参数改变的**相对幅度**。

**为什么比 grad norm 更好**：

grad norm = 5.0，这大不大？取决于参数本身的量级——对一个 $\|W\| = 10000$ 的权重矩阵来说微不足道，对 $\|W\| = 0.1$ 的来说天翻地覆。Update/weight ratio 自动归一化了这个差异。

**典型值**：~1e-3（每步改变参数的千分之一）。

**异常**：
- 爬升 → lr 对当前参数组偏大，或 Adam 的二阶矩（分母）在缩小
- 分层看能找到离群层 → 对该参数组单独降 lr

### 2.7 Throughput / MFU / Step Time——"钱花得值不值"

**Throughput**（tokens/sec）：每秒处理多少 token。这是最直接的"算力利用"指标。

**MFU**（Model FLOPs Utilization）：实际算力 / 硬件理论峰值。典型健康值 0.35~0.45。低于 0.3 说明有瓶颈（通信、IO、内存）。

**Step time**：完成一个训练步的时间。重点看 **P99**（最慢 1% 的步）而不是均值——P99 异常 = 有 straggler 节点。

| 异常模式 | 含义 |
|---|---|
| 突然下降（throughput 骤降 / step time 骤升） | 节点挂了、网络故障、GPU 降频 |
| 缓慢下降 | 内存泄漏（Python 对象累积）、数据序列越来越长、checkpoint IO 干扰 |
| P99 很高但 P50 正常 | 某个 rank 是 straggler，同步训练所有人等它 |
| 周期性毛刺 | checkpoint 保存、eval 运行等周期事件 |

**规模参考**：LLaMA 3 在 16K H100 上训 54 天，419 次意外中断里约 78% 归因于硬件，平均 3 小时一次。大规模训练里硬件故障不是意外，是日常。

### 2.8 SFT 专属指标

SFT 的核心转变：train loss 变得**不可靠**。数据量小、模型容量大，loss 一定会降，过拟合了也会降。所以 SFT 的监控重心从数值转向**行为**。

| 指标 | 它在量什么 | 为什么预训练不需要它 |
|---|---|---|
| **EOS 结束率** | 模型在自由生成时能否正确停下来 | 预训练是连续文本，没有"停"的概念；SFT 的对话格式必须学会在 `<\|im_end\|>` 处停止 |
| **Truncation 率** | 训练样本因超 max_length 被截断的比例 | 预训练文本本身就按长度切好了；SFT 的多轮对话容易超长，被截断 = 模型永远看不到 EOS → 学不会停 |
| **定期生成评审** | 固定 prompt 集，每个 checkpoint 实际生成，人+RM 打分 | 预训练阶段模型还不会对话，生成评审无意义 |
| **输出熵** | 词表概率分布的 Shannon entropy，衡量输出多样性 | 预训练多样性由数据保证；SFT 容易套路化（模板回复），熵塌缩 = 后续 RL 没有探索空间 |
| **通用能力回归** | SFT 前后跑 MMLU/GSM8K 级 benchmark 对比 | 预训练是在增长能力；SFT 可能因过拟合对话格式而丢失通用能力 |

**Truncation 率是训练前检查的**——不是训练中的指标，而是"开训之前必须确认的数据健康度"。超过 1% 就要处理（扩 max_length 或过滤超长样本）。

**EOS 结束率为什么特别重要**：teacher forcing 训练时，每一步的输入都是标准答案——模型不需要自己决定何时停止。只有在自由生成时，模型才需要自主输出 EOS。如果 EOS 结束率低，说明模型"学了格式但没学到停止"——这是 SFT 第一高发事故。

### 2.9 RL 专属指标

RL 的核心矛盾：**reward 上涨 ≠ 模型变好**。模型可能在 hack 评分规则（堆格式、注水、刷长度），proxy reward 涨了但真实能力没涨甚至退化。所有 RL 监控围绕两件事——**奖励是否可信**、**探索是否还活着**。

| 指标 | 它在量什么 | 为什么 RL 之前不需要它 |
|---|---|---|
| **Entropy** | 策略输出的概率分布有多"均匀"——高熵 = 多种 token 都有较大概率（探索活跃），低熵 = 几乎确定性输出（探索死亡） | 预训练/SFT 靠数据多样性保证探索，不需要显式监控 |
| **KL(π\|\|ref)** | 当前策略和 SFT 基线之间的距离。量化"模型偏离了 SFT 教的'正常行为'多远" | SFT 没有参考策略的概念 |
| **Proxy vs Gold 分叉图** | 同一批 held-out prompt，一条线画 proxy reward（RM 打分），另一条线画 gold 评估（人工/规则/更强的 judge）。两条线分叉 = Goodhart 定律生效 | 预训练/SFT 不涉及 reward |
| **Response length** | 生成文本的长度分布 | RL 中持续膨胀 = RM 的长度偏好被 hack（最经典的 reward hacking） |
| **零优势组占比**（GRPO 专有） | 一组 rollout 全对或全错 → 组内优势全为 0 → 不产生梯度 | PPO 用 critic 给每个 token 打分，不存在"整组零优势"的问题 |

**Entropy 是 RL 的头号先行指标**：

```
entropy 健康下降：正常——模型学到了好策略，不再随机探索
entropy 持续走低到接近 0：危险——模型失去了尝试新回答的能力，能力封顶
entropy 突然飙高：失稳——策略被打乱，需要检查 lr 和 reward signal
```

DAPO 的 clip-higher 机制就是专门针对 entropy 塌缩开的药——当模型的动作概率超过参考策略太多时，不 clip（允许减小该动作概率），鼓励保持探索。

**Proxy vs Gold 分叉图是 RL 最重要的一张图**：

```
健康:  proxy ↑  gold ↑   → 奖励模型可信，模型真的在变好
正常:  proxy ↑  gold →   → 边际收益递减，考虑停训
危险:  proxy ↑  gold ↓   → Goodhart！模型在 hack RM，立刻停或换 RM
```

### 2.10 不需要日常监控的指标

| 指标 | 为什么不日常看 | 什么时候用 |
|---|---|---|
| 逐层 grad norm | 日常信息量太低（几十层几十条线看不过来） | 出事后排查时临时开：定位最先异常的层 |
| bits-per-byte | 跨 tokenizer 时才需要的 loss 归一化方式 | 和别人的模型比 loss 时 |
| gradient noise scale | batch size 选择的一次性测量 | 训练前调参时 |
| distinct-n | 文本多样性统计 | 人工抽查能覆盖，自动化价值低 |

同一个指标在不同阶段的**重要性和含义完全不同**。

| 指标 | 预训练 | SFT | RL |
|---|---|---|---|
| **Train loss** | ★★★ 主信号 | ★☆☆ 不可靠（记忆效应） | ★☆☆ 被 reward 取代 |

| **LR 曲线** | ★★★（长 run，resume 事故多） | ★★☆ | ★★☆ |

| **Update/weight ratio** | ★★☆ lr 是否偏大 | ★★☆ | ★☆☆ |
| **Throughput/MFU** | ★★★ 长 run 必须 | ★☆☆ 训练快，浪费有限 | ★★☆ rollout 是瓶颈 |
| **EOS 结束率** | — | ★★★ 第一高发事故 | — |
| **定期生成评审** | ★☆☆ | ★★★ | ★★★ |

| **Proxy vs Gold** | — | — | ★★★ 最重要的一张图 |
| **Response length** | — | ★★☆ 观察分布 | ★★★ hack 信号 |

**为什么重点在移动**：

- **预训练**：数据量大、训练长，最大风险是数值崩溃和慢性遗忘 → 重点看数值稳定性和分域效果
- **SFT**：数据量小、训练短，最大风险是过拟合和格式问题 → 重点看行为指标（EOS、生成质量）
- **RL**：reward signal 取代了 loss → 重点看 reward 是否可信（Goodhart）和策略是否还在探索（entropy）

## 4. 诊断方法论——训练出问题了，按什么顺序排查

上面讲的是"看什么"。这节讲"看到异常后怎么定位原因"。

训练故障按**时间形态**分四类，每类的先行指标和排查路径不同：

| 类型 | 时间形态 | 先行指标 | 典型根因 | 首选解法 |
|---|---|---|---|---|
| **脉冲型** | 单步 spike | 无（grad norm 同帧跳） | 脏数据、数值溢出、硬件 | clip 兜底；回滚 + 跳 batch |
| **漂移型** | 几百步渐变后突然崩 | max logits 爬升（提前几百步） | QK 范数正反馈 | QK-Norm / QK-Clip |
| **慢性病型** | 万步级看不出，评估才发现 | 分域 val loss 分叉 | 配比漂移、数据质量、能力挤占 | 修配比 / 洗数据 / replay |
| **僵尸型** | loss 正常但效率在跌 | throughput / step time P99 | 硬件故障、straggler、内存泄漏 | 逐 rank 定位 + 热备替换 |

**鉴别关键**：

- 看到 spike → 先往回看几百步：有没有慢变量在爬升？有 = 漂移型（2），无 = 脉冲型（1）
- loss 在降但 benchmark 停滞 → 查分域 val loss = 慢性病型（3）
- 什么指标都正常但训练速度变慢了 → 僵尸型（4）

### Spike 应对标准流程

```
1. grad norm 报警 → 看 loss 是否也跳了？
   - 只 grad 跳、loss 没动 → clip 兜住了，记录但继续
   - 两个都跳 → 等 1~2 步看是否自愈

2. 自愈（回落到正常区间）→ 记录 step + batch 位置，继续
   同一数据源反复 spike → 清洗该数据源

3. 不自愈 → 停训，逐个排查：
   a. 是不是漂移型？回看前几百步慢变量有没有爬升
   b. 脏数据？回溯 spike 那个 batch（乱码？超长？重复？）
   c. 硬件？查 ECC 错误日志、网络抖动、多 rank 梯度一致性
   d. 数值溢出？挂 hook 找第一个出现 Inf/NaN 的层
      → 嫌疑：softmax / LayerNorm / embedding → 该算子提 fp32

4. 恢复：回滚到最近健康 checkpoint + 跳过此后 200~500 batch
   （PaLM 标准操作——spike 后的数据可能"带菌"）
   反复 spike 且排除了数据和硬件 → 降 lr 重启（OPT 方案）
```

**spike 后看最先异常的层——指向三种有名字的病**：

| 最先异常的层 | 对应的病 | 出自 | 解法 |
|---|---|---|---|
| embedding 层 | embedding 梯度病态地大 | GLM-130B | DeepNorm + Embedding Gradient Shrink |
| attention 的 Q/K | attention logits 漂移 | ViT-22B / Kimi K2 | QK-Norm / QK-Clip |
| 输出层（lm_head） | 输出 logits 尺度过大 | PaLM | z-loss |

## 5. Scaling Law 与运行时异常检测

Chinchilla 论文的核心：训练几百个不同大小的模型，记录 held-out validation loss，拟合经验公式：

$$L(N, D) = \frac{A}{N^\alpha} + \frac{B}{D^\beta} + E$$

训练过程中反过来用它做**运行时异常检测**：把初期 loss 曲线拟合成预测曲线，持续对比实际 loss vs 预测 loss。偏离预测曲线 = 最宏观的"有什么不对"信号。

**为什么用 validation loss 而非 training loss**：大模型的记忆效应使 training loss 偏低，不同大小模型间不可比。Validation loss 测的是"没见过的数据上的表现"，才具有可比性。

## 6. 事故案例库

面试时引用真实病历比讲概念更有说服力。

| 案例 | 哪类故障 | 关键信号 | 怎么救的 | 面试可说的一句话 |
|---|---|---|---|---|
| **OPT-175B** | 脉冲型 | 反复 spike + PPL 发散 | 降 lr 重启、换 fp32、跳坏数据 | "降 lr 重启"这个做法的原始出处 |
| **PaLM** | 脉冲型 | ~20 次 loss spike | 回滚 ~100 步 + 跳 200~500 batch | spike 后的数据要跳过，不是重放 |
| **GLM-130B** | 脉冲型 | 训练初期反复 spike | DeepNorm + Embedding Gradient Shrink | spike 后看**哪一层先爆**比数值本身更有信息量 |
| **ViT-22B** | 漂移型 | ~2000 步后 logits 涨到 50,000+ | QK-Norm | 漂移型崩溃的标准教科书案例 |
| **Kimi K2** | 漂移型 | 中期 max logits 冲破 1000 | QK-Clip（τ=100），仅 12.7% 的头触发 | 监控 → 根因 → 最小干预的完整闭环 |
| **DeepSeek-V3** | 无病 | 14.8T tokens 零回滚 | FP8 + 工程体系预防 | "零事故"是设计出来的，不是运气 |
| **LLaMA 3** | 僵尸型 | 16K H100，54 天 419 次中断 | 自动检测 + 热备替换 | 大规模训练里硬件故障是日常不是意外 |

**2026 趋势**：一线团队在把"监控 → 抢救"变成"设计 → 免疫"——DeepSeek-V4 把稳定性直接写进架构（Muon + mHC），但**监控依然是验证免疫有效的唯一手段**。

## 面试话术

> "训练监控我有完整方法论。核心是分三层看：每步数值（loss、grad norm）管生死——spike 了立刻排查数据和数值；慢变量（max attention logits、update ratio）管预警——漂移型崩溃提前几百步就有信号；定期评估（分域 val loss、benchmark）管方向——发现遗忘和配比问题。
>
> 重点说两个我印象深的：第一，train loss 降不代表模型变好——SFT 阶段 loss 降可能是在背数据，RL 阶段 reward 涨可能是在 hack RM。所以不同阶段主信号不同：预训练看 val loss，SFT 看生成质量和 EOS 结束率，RL 看 proxy vs gold reward 有没有分叉。
>
> 第二，attention logits 漂移是我觉得最有意思的故障——它背后是一个正反馈回路：训练鼓励尖锐 attention → Q/K 范数变大 → logits 变大 → softmax 更尖 → 进一步推高。ViT-22B、Kimi K2 都撞过。MiniMind 里我也加了 QK-Norm 做架构级预防。这个病的特点是 grad norm 和 loss 在崩溃前几百步完全正常，只有 max attention logits 曲线在爬升——所以慢变量监控不能省。"
