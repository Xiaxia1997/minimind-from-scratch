# 10b - 训练过程监控

> 前置：[10-训练阶段论](10-训练阶段论.md)（训练管线全景、各阶段数据/Loss/学习率差异）
> 参考：Kimi K2、DeepSeek-V3/V4、LLaMA 3、GLM-5、OPT-175B 技术报告
>
> **原则**：不大而全。每个指标必须回答——"它比什么手段更早发现什么问题？"答不上来的删掉。面板上多一个无用指标不只是浪费，它会稀释你对关键指标的注意力。

---

## 0. 监控只回答三个问题

所有指标本质上只回答三件事：

1. **活着没**（稳定性）：数值上是否正常运行，会不会突然崩或慢性死亡
2. **学好没**（效果）：能力是否按预期增长，算力花得值不值
3. **跑快没**（效率）：硬件是否跑满，有没有隐性减速

第二个维度是**时间分辨率**——不同频率的指标能抓到的故障类型完全不同：

| 频率 | 能抓什么 | 抓不到什么 |
|---|---|---|
| 每步 | 急性故障（spike、NaN、节点挂掉） | 慢性病（配比失衡、遗忘） |
| 每百~千步 | 慢性漂移（logits 爬升、val loss 停滞） | 单步事故（间隔内自愈就漏掉） |
| 每千~万步 | 能力增长趋势、reward hacking 分叉 | 一切急症 |

所以监控必须是**多层组合**，单层指标必有盲区。

## 1. 训练的四种死法

先认清敌人，再配武器。训练故障按时间形态分四类，每类需要不同层级的指标来捕捉。

### 1.1 脉冲型（单步 spike）

**面板上看到**：grad norm 和/或 loss 单步跳升数倍。

**先厘清 "spike" 到底指什么**——实践中混指三种现象，处理完全不同：

| 现象 | 面板表现 | 含义 |
|---|---|---|
| **loss spike** | train loss 单步跳升 | 这个 batch 上模型预测突然变差 |
| **grad norm spike** | 梯度范数单步跳升 | 这一步更新试图把参数推得很远 |
| **慢变量爬升** | max attention logits、update ratio 几百步缓慢上涨 | 内部统计量正在走向失控（它不是 spike，但常以 spike 收尾）→ 属于 1.2 漂移型 |

两条曲线（loss + grad norm）都要画。看到任一跳升，先看另一条确认。**排查原则：先异常的指标是因，后异常的是果——顺着时间最早的信号查。**

**病因只有三类**：脏数据、数值溢出、硬件。

**发现 spike 后的操作流程**：

**第 0 步｜确认现象。** grad norm 和 loss 是否同帧跳？只有 grad spike 而 loss 没动 = clip 兜住了，伤害被限幅但没消除，仍要记录。

**第 1 步｜等 1~几步，看是否自愈。**
- **自愈**（grad norm 回到原区间、loss 回落）→ 不停训。记录 step 和 batch 位置，事后回溯；同一数据源反复引起自愈型 spike → 清洗那个源
- **不自愈**（loss 停在高位 / 反复 spike / 出现 NaN）→ 停训，进第 2 步

**第 2 步｜按排查成本从低到高逐个排除**：

| 顺序 | 查什么 | 怎么查 | 查到后怎么办 |
|---|---|---|---|
| a | **是不是伪装的漂移型** | 回看 spike 前几百步的慢变量（max attention logits、update ratio）有没有爬升 | 有爬升 → 转 1.2 流程 |
| b | **脏数据** | 回溯 spike 那个 batch：乱码？超长？重复序列？格式异常？ | 清洗 + 跳过该段数据 |
| c | **硬件** | 同时段 Xid/ECC 日志、网络抖动；多 rank 对比该 step 的梯度是否一致 | 隔离换节点 |
| d | **数值溢出** | 挂 hook 找前向/反向中第一个出现 Inf/NaN 的层和算子 | 嫌疑：softmax / LayerNorm / embedding → 提到 fp32 计算 |

**第 3 步｜恢复训练。** 回滚到最近健康 checkpoint + **跳过此后 200~500 个 batch**（PaLM 标准操作——spike 之后的数据可能"带菌"，要跳过不是重放）。反复 spike 且排除了数据和硬件 → 降 lr 重启（OPT 方案）。

**进阶：最先异常的层，指向三种有名字的病**

spike 后看**哪一层先爆**，直接对应三个文献里有完整病历的故障：

| 最先异常的层 | 对应的病 | 解法 |
|---|---|---|
| embedding 层 | **GLM-130B 的病**：embedding 梯度病态地大 | DeepNorm + Embedding Gradient Shrink |
| attention 的 Q/K | **ViT-22B / Kimi K2 的病**：attention logits 漂移（详见 1.2） | QK-norm / QK-Clip |
| 输出层（lm_head） | **PaLM 的病**：输出 logits 尺度过大 | z-loss（2022 方案；现代架构已少见此病） |

> **MiniMind 在 [04-Attention](04-Attention.md) Step 3 加了 QK-norm**——不是可选的花哨功能，而是防第二种病的架构级预防。

### 1.2 漂移型（慢变量爬升后发散）⚠️ 最该重点理解的死法

**机制——本质是"无约束自由度 + 训练激励同向"形成的正反馈回路**：

1. 网络里存在某个**不受约束的统计量**（如 QK 的范数 → attention logits 尺度）
2. **训练目标本身鼓励它变大**（尖锐的注意力需要大的 logit 差）
3. 正反馈形成：统计量增长 → softmax 趋近 one-hot → 梯度病态 → 参数更新进一步推高 → ……
4. 越过数值临界点后崩盘。**崩盘的最后一步表现为 spike，但前面有几百到几千步的爬升期**——这是它和死法一的鉴别点

```
训练初期:  attention logits max ≈ 20~30   → softmax 正常
训练中期:  attention logits max ≈ 50~80   → softmax 精度开始下降
训练后期:  attention logits max ≈ 200+    → BF16 溢出 → NaN → spike
```

实例：ViT-22B 约 2000 步后 attention logits 涨到 50,000+ 后发散；Kimi K2 中期实验 logits 冲破 1000。

**定位**：
1. 看慢变量曲线（max attention logits、update ratio）：**哪个在爬升？爬升是否加速**——指数型加速 = 正反馈确认
2. **逐层逐头分解**：漂移通常不是全网均匀的。K2 全程只有 12.7% 的注意力头触发过 clip——**看 max 不看 mean**，均值会把病灶平均掉
3. spike 前有爬升 → 死法二；无爬升 → 死法一

**解决**：给无约束的自由度加最小必要的约束——
- **attention logits**：QK-Norm（Qwen3、Gemma 3、OLMo 2、GLM-4.5、MiniMind）或 QK-Clip（Kimi K2）
- **MoE router**：aux-loss-free 偏置调节（DeepSeek-V3/V4、GLM）
- 事中抢救：降 lr + 回滚到爬升起点前 + 上好约束再续训。不带约束直接续训 = 等着在同一位置再崩一次

### 1.3 慢性病型（配比 / 质量 / 遗忘）

**为什么每步指标完全看不出来**：梯度由当前 batch 决定。每个域的梯度都"正常"、总 loss 在降，问题被加权平均掩盖了。

三种病因：
- **配比漂移**：某域实际消费量偏离计划——采样 bug，或某数据源耗尽后被动重配
- **质量塌方**：某域数据重复率高、被污染、格式不一致
- **能力挤占**：某阶段单域占比过高，其他领域被遗忘

**定位**：
1. **分域 val loss**：哪条曲线停滞或回升？总 loss 降而某域升 = 强信号
2. **对照数据消费日志**：实际消费的 token 数和占比 vs 计划配比——分清"吃错了"还是"数据本身坏了"
3. **benchmark 分任务趋势**交叉验证
4. **probe set 跨 run 对比**：排除"验证集本身有问题"的假警报

**解决**：
- 配比错 → 修采样权重
- 质量坏 → 去重、过滤、重洗
- 遗忘 → 回混早期领域数据（replay）+ 降 lr
- **元原则**：配比决策先用同族小模型的 scaling 实验验证，不要在大 run 上边训边调

### 1.4 僵尸型（硬件 / 效率）

**机制**：loss 完全正常，钱在烧。同步训练里所有 rank 等最慢的一个；silent data corruption 能算但算错、无报错。

规模参考：LLaMA 3 在 16K H100 上训 54 天，419 次意外中断里约 78% 归因于硬件，平均 3 小时一次。大规模训练里这不是意外，是日常。

**定位**：
1. **step time P99/P50 比值**：比值异常 = straggler 存在（看 P99 不看均值）
2. **逐 rank 计时分解**（计算 vs 通信 vs IO）：定位是哪个 rank、哪个环节慢
3. throughput **突降** = 节点/网络事件；**缓降** = 内存泄漏或序列变长
4. silent data corruption：定期数值校验——固定 batch 复算 loss、跨节点梯度一致性检查

### 速查表

| | 时间形态 | 先行指标 | 首选定位工具 | 首选解法 |
|---|---|---|---|---|
| **脉冲型** | 单步突变 | 无（grad norm 同帧） | 逐层 grad norm + batch 回溯 | clip 兜底；回滚 + 跳 batch |
| **漂移型** | 渐变后突变 | 慢变量爬升（提前百~千步） | max logits 曲线，逐头分解 | 加最小约束（QK-Norm/QK-Clip） |
| **慢性病型** | 万步级渐变 | 分域 val loss 分叉 | 数据消费日志 vs 计划配比 | 修配比 / 洗数据 / replay |
| **僵尸型** | 随机 | throughput、step time P99 | 逐 rank 计时分解 | 自动检测重启 + 热备替换 |

**四种死法对应四层指标**——每步数值（死法一）、慢变量（死法二）、定期评估（死法三）、吞吐（死法四）。缺一层就有一类故障在裸奔。

## 3. 事故案例库

真实病历，面试可引用。

| 案例 | 症状 | 根因 | 处理 | 教训 |
|---|---|---|---|---|
| **OPT-175B**（2022） | 反复 spike + PPL 发散；两个月 35 次人工重启 | lr 过大 + 数值不稳 | **降 lr 重启**、换 fp32、跳坏数据 | "降 lr 重启"这个说法的真正出处 |
| **PaLM**（2022） | 约 20 次 loss spike | 输出 logits 过大 | 回滚 ~100 步 + **跳过 200~500 batch** | spike 后的数据可能"带菌"，要跳过 |
| **BLOOM**（2022） | 全程仅 1 次 spike 且自愈 | — | embedding 层后加 LayerNorm 预防 | 架构预防 > 事中抢救 |
| **GLM-130B**（2022） | 训练初期反复 spike | **embedding 层**梯度异常 | DeepNorm + Embedding Gradient Shrink | spike 的**位置**信息量比数值大 |
| **ViT-22B**（2023） | 约 2000 步后发散 | attention logits 涨到 50,000+ | QK-norm | 漂移型标准病历 |
| **DeepSeek-V3**（2024） | 无病 | FP8 + 工程体系预防 | 14.8T tokens 零回滚 | "零事故"是设计出来的 |
| **Kimi K2**（2025） | 中期 max logits 冲破 1000 | Muon 优化器放大 QK 权重 | **QK-Clip**（τ=100），仅 12.7% 的头触发 | 监控 → 根因 → 最小干预的完整闭环 |

**2026 趋势**：一线团队正在把"监控 → 抢救"变成"设计 → 免疫"——DeepSeek-V4 把稳定性直接写进架构（Muon + mHC），但**监控依然是验证免疫有效的唯一手段**。

## 4. Scaling Law 与运行时异常检测

Chinchilla 论文的核心：训练几百个不同大小的模型，记录 held-out validation loss，拟合经验公式：

$$L(N, D) = \frac{A}{N^\alpha} + \frac{B}{D^\beta} + E$$

训练过程中可以反过来用它做**运行时异常检测**：把初期 loss 曲线拟合成预测曲线，持续对比实际 loss vs 预测 loss。偏离预测曲线 = 最宏观的"有什么不对"信号。

**为什么必须用 validation loss 而非 training loss**：大模型的记忆效应使 training loss 偏低，不同大小模型间不可比。Validation loss 测的是"没见过的数据上的表现"，才具有可比性——这正是 Scaling Law 要回答的问题。

## 一页纸总结

```
每步（4）：   train loss · grad norm(+clip触发率) · LR · NaN/skip
慢变量（2+）：max attention logits · update/weight ratio（MoE 加 expert 均衡）
定期（3）：   分域 val loss · probe set loss · benchmark 曲线
效率（2）：   throughput/MFU · step time P99
SFT 加（4）： EOS 结束率 · truncation率(训前) · 定期生成评审(人+RM) · 输出熵
RL 加（4）：  entropy · KL · 零优势组占比 · proxy vs gold 分叉图
```

三条军规：

1. **每步指标管生死，慢变量管预警，定期指标管方向**——三层缺一，必有裸奔的故障类型
2. **任何"在涨"的指标都要问：是真的变好，还是在 hack 度量本身**——reward、length、val loss 都适用
3. **人工抽查生成样本，是任何阶段都删不掉的监控项**
